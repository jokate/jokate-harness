## Q1. What do developers (and agents) actually query, how often, and in what patterns?

### Takeaway
At Google, developers run code search about 5 sessions and 12 queries per workday (2015). That figure is about 7 queries per user per day in a 2025 re-study of more than 100,000 users. Sessions are short (median 90 s) and usually target code the developer already partly knows. Query intent splits roughly into: how/usage examples about one third, what/browsing about one quarter, where/location about 16%, why about 16%, and who/when about 8%. "Where" questions cover definitions and "all usages of an API", and they are answered by search or semantic links such as jump-to-definition. Coding agents spend their early turns on reproduction and localization. In a 2026 preliminary study, agents chose a semantic (LSP) tool unprompted on reference-finding tasks (45–57% of the time) but almost never for localization, where they defaulted to grep.

### Inferences
- In our tool's terms, the human-side query mix maps as follows. "How" (about a third of searches: usage examples of an API they already know) is a **find-references/callers** query on a known symbol where the developer wants a few good examples, not all of them. "Where" (about 16%) is **exact lookup / definition / all usages**. "What" (about a quarter) is **symbols-in-file, members, call hierarchy**. So reference-style queries on popular symbols sit behind the single largest intent class. That is where our slow path (hot-symbol reference aggregation) bites.
- Reachability (caller-chain/impact) questions are reported as frequent and hard. Fast multi-hop callers and impact queries are therefore high-value, not niche.
- Agents follow localization-then-zoom. They pick semantic tools mainly for reference-completeness tasks, so references/callers are the semantic queries agents will actually issue. Substring symbol search competes with grep, which agents default to anyway.

- I could not open the full Sadowski 2015 paper to confirm per-category percentages, queries per session, or the share of queries using `file:`/`lang:` filters.
- No IntelliJ/VS Code telemetry paper with "Find Usages / Go to Definition" invocation shares was found. Amann et al. (SANER 2016, Visual Studio usage) and the KaVE/FeedBaG dataset (MSR 2018 challenge: >11M events, 15K hours, 81 developers) exist, but I could not retrieve navigation-command shares ([MSR 2018 challenge](https://2018.msrconf.org/track/msr-2018-Mining-Challenge)).
- No Bing/Microsoft internal code-search query-log study with intent shares was found. The Rahman et al. study uses Google web search, not Bing.
- No study measures the query mix of LLM agents against a C++ semantic index specifically.

## Q2. What latency is acceptable for interactive code navigation (human) and for agent tool calls?

### Takeaway
The classic thresholds are 0.1 s (feels instantaneous), 1 s (flow preserved) and 10 s (attention lost). Google's Code Search team uses a stricter, code-specific target: **sub-200 ms end-to-end for all frequent operations**. Their search backend runs at a median server-side latency under 50 ms. For agents, peer-reviewed thresholds do not exist. Workload studies put tool or environment time at roughly 17–60% of agent wall-clock, depending on harness. A few long calls (builds, tests) dominate, so per-query index latency in the tens to hundreds of ms is a small share of an agent turn. Output size and token cost matter more.

### Cited Findings
- Nielsen, *Usability Engineering* (1993), ch. 5, building on Miller (1968) and Card et al. (1991): **0.1 s** is the limit for the system to feel like it reacts instantaneously; **1.0 s** is the limit for the user's flow of thought to stay uninterrupted, though the delay is noticed; **10 s** is the limit for keeping attention on the dialogue, beyond which a progress or completion estimate is needed. [primary-snippet] — [NN/g article](https://nngroup.com/articles/response-times-3-important-limits)
- Google SWE book ch. 17 [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html):
  - "A UI is considered responsive if latencies are below 200 ms. But after just one second, the developer's attention often begins to drift. If another 10 seconds pass, the developer is likely to switch context completely… The best way to keep a developer in the productive 'flow' state is by targeting **sub–200 ms end-to-end latency for all frequent operations**."
  - Economics: "For one million queries, an increase of just one second per search request corresponds to about 35 idle full-time engineers every day… with about 100,000 queries per day (corresponding to less than 5,000 developers), just the one-second latency argument is something of a break-even point."
  - Achieved: "Code Search indexes about 1.5 TB of content and processes about 200 queries per second with a **median server-side search latency of less than 50 ms** and a median indexing latency… of less than 10 seconds."
  - "As an interactive tool, Code Search must be fast, allowing a 'question and answer' workflow. It is expected to have low latency in every respect: search, browsing, and indexing."
- Google "Speed Matters" experiments (Brutlag, 2009): slowing the search results page by **100–400 ms** reduced searches per user by **0.2–0.6%**. [primary-snippet] — [Google Research blog](https://research.google/blog/speed-matters/); [PDF](https://services.google.com/fh/files/blogs/google_delayexp.pdf)
- Arapakis, Bai & Cambazoglu, SIGIR 2014 (Yahoo): added delays "became noticeable once they exceeded a certain threshold". Users of fast systems noticed delays more than users of slow systems. Given identical results, users preferred clicking the lower-latency page. The numeric threshold was not visible in the abstract. [primary-snippet] — [TOIS 2017 extension record](https://ir.webis.de/anthology/2017.tois_journal-ir0anthology0volumeA36A2.10/); [Paper Digest](https://www.paperdigest.org/certificate/2b8908697297a0d4)
- GitHub's new code search (Blackbird, 2023): 45M repos, 115 TB, 15.5B documents; about **640 QPS vs ~0.01 QPS for ripgrep**; indexing about 120,000 docs/s. The stated original goal was "< 1 second for 95 percent of users on global queries, and faster still for more narrowly scoped queries". [secondary: The Register reporting GitHub's post] — [The Register](https://www.theregister.com/2023/05/09/blackbird_github_search/); [GitHub blog](https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/)
- GitHub incident, 2026-02-23/24: one search query "concentrated load on a single hot shard within the search index, slowing down all queries", and 5–10% of queries timed out. [primary-snippet] — [GitHub status incident](https://www.githubstatus.com/incidents/jn8kcmg5ydch)
- Agents: Bian et al., "What Limits Agentic Systems Efficiency?" (arXiv 2510.16276, NeurIPS 2025 venue listing) found that web-environment latency "can contribute as much as **53.7%**" of overall latency in web agents (an upper bound). Speculative caching cut that overhead up to 3.2× (3.51× in the NeurIPS version). The authors note that "both the number of rounds and the total tokens generated per round" are major bottlenecks. [primary-snippet] — [arXiv 2510.16276](https://arxiv.org/html/2510.16276v1)
- Coding-agent tool-time shares conflict across 2026 workload papers. One study finds local Bash about 39% of latency on coding benchmarks. PASTE (speculative tool execution) reports about 60% in coding tasks (SWE-bench/OpenHands profiles). A workload characterization finds LLM inference at 71–98% of runtime, with tools at 17.7% on SWE-bench Pro. In mini-SWE-agent SWE-bench runs, "fewer than three percent of tool calls hold almost two thirds of all tool time" (installs, builds, test suites). [secondary: search summaries; attribution between papers not individually verified] — [PASTE arXiv 2603.18897](https://arxiv.org/html/2603.18897v1); [Agentic AI Workload Characterization arXiv 2605.26297](https://arxiv.org/html/2605.26297v2); [Not All AI Agents Are Equal arXiv 2609.19947](https://arxiv.org/pdf/2609.19947); [Ask the Tool, Don't Guess arXiv 2609.18849](https://arxiv.org/html/2609.18849)
- SWE-agent's design argument: iterative, one-result-at-a-time search "can exhaust an agent's cost budget or context window". In agents, the cost of a bad interface shows up as turns and tokens, not milliseconds. [primary-snippet] — [SWE-agent arXiv 2405.15793](https://arxiv.org/pdf/2405.15793)

### Inferences
- **Human webview budget.** One click fires several queries, so the 200 ms end-to-end target applies to the click, not to each query. Each query in a 3–5-query click should therefore be about 50 ms or less (p50), with p95 well under 200 ms, if run serially. The 1 s threshold is the outer limit before flow breaks. The slow paths (hot-symbol reference aggregation, leading-wildcard scans) need to fall under these bounds, or return a partial or ranked answer within budget.
- **Agent CLI budget.** An agent turn includes an LLM call that typically takes seconds, and tool time is dominated by a few long builds or tests. An index query of 100–500 ms is therefore unlikely to dominate agent wall-clock. This is an inference; no source measures navigation-tool latency specifically. For agents, the priorities are (a) avoiding multi-second outliers on hot symbols, which do show up, (b) per-process startup cost, since a CLI-per-query design pays it every call, and (c) above all, **output size**, because tokens and context use drive cost and accuracy (see Q5).
- The GitHub hot-shard incident is the operational form of the heavy-tail problem: one pathological query can degrade everyone. Our analogue is that one `check`/`TEXT`/`FString` reference query must not stall the webview or the CLI.

### Gaps
- The numeric noticeability threshold from Arapakis et al. 2014 could not be retrieved.
- No peer-reviewed study gives acceptable latency for agent tool calls specifically, or measures how navigation-tool latency (as opposed to build/test) affects agent success or cost.
- Numbers for GitHub Blackbird's p50/p99 latency were not found in accessible sources.

## Q3. How are scalable, incremental code-navigation and cross-reference indexes designed?

### Takeaway
Production systems separate a fast, incremental **text/substring index** (trigram or sparse n-gram, updated within seconds) from a **semantic cross-reference graph**. The graph is built at global scale per build unit and merged: Google rebuilds it daily (about 6 h for Chromium), while Meta's Glean updates it incrementally through stacked immutable databases with per-unit fact ownership. Precomputation of derived facts makes find-references fast. Results are ranked with sharding by priority, and complete result sets are fetched only on demand. For merging a small fresh index with a large stale one, clangd's own MergedIndex makes the fresh index authoritative for the files it covers and streams results under a limit. Glean's stacked DBs hide excluded units from the base DB.

### Cited Findings
**Google (Grok → Kythe; Code Search)** [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)
- "Kythe instruments the build workflow to extract semantic nodes and edges… collects partial cross-reference graphs for each individual build rule. In a subsequent phase, these partial graphs are merged into one global graph and its representation is **optimized for the most common queries (go-to-definition, find all usages, fetch all decorations for a file)**. Each phase… is roughly as expensive as a full build; for example, in case of Chromium, the construction of the Kythe index is done in about **six hours** in a distributed setup… the Kythe index is computed only once per day." (footnote 8)
- "The cross-reference index cannot be instantly updated… any code change can potentially influence the entire codebase, and in practice often does affect thousands of files." The text search index, by contrast, is incremental: "only the actual files touched need to be reindexed." The gap between the instant and the daily index is "a source of rare but recurring issues."
- The substring index evolved "from the original trigram-based solution, through a custom suffix array–based solution, to the current sparse n-gram solution". The index moved from RAM to flash, which changed which index designs worked ("the original trigram index requires fetching… a large number of reverse indices… and quite large ones").
- Brute force is infeasible at that scale: RE2 runs at about 100 MB/s, so 1.5 TB in 50 ms would need about 300,000 cores.
- Trigram trade-off: "the small size comes at the cost of relatively low recall accuracy [i.e., many false candidates] compared to other substring indices. This means slower queries because the nonmatches need to be filtered out." A regex can be converted into substring lookups, and "only a small fraction of user queries are complex regular expressions."
- Ranking: "In Google's codebase, any short substring will occur thousands, if not millions, of times. Without ranking, the user either must check all of those results… or must refine the query." Signals include a PageRank-like count of **references to a file** (include/import edges, later taken from the Kythe graph). These query-independent signals are computed offline.
- **Completeness vs relevance**: "ranked search is the more common case in which the user is looking for one particular thing… However, sometimes developers want all results; for example, finding all occurrences of a particular symbol for refactoring." The solution: "split the codebase into shards with files ordered by their priority. Then, we usually need to consider only the matches to high priority files from each chunk… if requested, Code Search can fetch all results… without typical searches being slowed down." Footnote 16 adds that safeguards exist "so that responses don't become painfully huge… (imagine searching for the letter 'i' or a single space)."
- History: Grok was proposed or built by Steve Yegge around 2008 and later open-sourced as Kythe. Google's 2020 open-source Code Search blog describes merging per-language Kythe graphs, pruning, and optimizing for serving cross-references, running "several times per day". That conflicts with the SWE book's "once per day", likely because they describe different deployments or dates. [primary-snippet] — [Google Open Source Blog 2020](https://opensource.googleblog.com/2020/04/code-search-for-google-open-source.html); [Wikipedia: Google Kythe](https://en.wikipedia.org/wiki/Google_Kythe); [Yegge Stanford EE380 abstract](https://web.stanford.edu/class/ee380/Abstracts/Yegge.html)
- Russ Cox (2012), "Regular Expression Matching with a Trigram Index (or: How Google Code Search Worked)". The regex is turned into an AND/OR query over trigrams, the posting lists are intersected, and candidates are verified with the real regex (RE2). The indexer skips files that look uninteresting, such as very long lines or a huge number of distinct trigrams. [secondary summaries of primary] — [Wikipedia: Trigram search](https://en.wikipedia.org/wiki/Trigram_search); [swtch.com article (blocked; cited by SWE book fn.18)](https://swtch.com/~rsc/regexp/regexp4.html)
- GitHub Blackbird uses **sparse n-grams rather than trigrams**, because trigrams "aren't quite selective enough" for code full of 3-letter tokens like `for`. It is sharded by Git blob ID, with each shard consuming its own Kafka partition. [secondary] — [Simon Willison's notes](https://simonwillison.net/2023/Feb/6/github-code-search); [GitHub blog](https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/)

**Meta Glean (open source; RocksDB-backed fact store)** [primary-read]
- Glean answers "Where is the definition of this method? Where are all the callers of this function? Who inherits from this class? What are all the declarations in this file?" "accurately and efficiently on a large-scale codebase". Facts are immutable, form a DAG, and are de-duplicated. Its query language Angle is Datalog-like (non-recursive) and **derives new facts by rules**. Glass is a symbol server, and there is a generic LSP server. "We typically store only the parts we need… locations of definitions and cross-references, but not expressions." — [Glean docs: Introduction](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/introduction.md)
- Incrementality design — [Glean docs: Incrementality](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/implementation/incrementality.md):
  - Every fact has an owner **unit**, which is an arbitrary string such as a file. Ownership sets are unit | OR-of-sets | AND-of-sets. "Typically we see between **10-100x more facts than sets**… one unit per file or module is good, but one unit per function would lead to more sets."
  - An incremental DB "*exclude[s]* some units from the base DB" through a **slice**, a bitmap over ownership sets. A fact is visible if its set is in the slice. Ownership propagates so that no visible fact references an invisible one, in O(facts) time.
  - **Derived facts** get the conjunction of their inputs' owners, so they disappear when any input is hidden.
  - **Stacked DBs**: a new DB layered on a base DB can add owners to base facts. The doc notes an unfinished edge case, incremental re-derivation over the stack.
  - Fact ownership is cached in memory, page by page, because checking visibility on each fact visit "can be very expensive."
- Meta's Dec 2024 engineering post describes a shared central index ("so that we don't repeat the work of indexing on every developer's machine"). Per a newsletter summary, it describes incremental indexing as "a stack of immutable databases". [primary-snippet / secondary] — [Meta Engineering, "Indexing code at scale with Glean"](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/); [TLDR summary](https://tldr.tech/dev/2024-12-20)
- An independent (non-Meta) benchmark indexed Hackage with Glean and compared it with hiedb. Find-references took 2.3 s on hiedb vs **0.39 s** through Glean/Glass vs **0.03 s** as a raw Glean query. The Glean DB was about 0.8 GB vs 5.2 GB for hiedb. The author credits the speed to stored derived predicates. Methodology is unverified. [secondary] — [segmentfault write-up](https://segmentfault.com/p/1210000047124675)

**GitHub stack graphs (precise navigation without builds)**
- Creager & van Antwerpen, "Stack graphs: Name resolution at scale", arXiv 2211.01224, Eelco Visser Commemorative Symposium (EVCS) 2023. Stack graphs extend scope graphs, and resolving a reference becomes a path-finding search. "Each source file becomes its own subgraph… graph construction and path-finding don't need any knowledge of, or visibility into, any other file", so "reanalyzing file versions that we have already seen can be avoided". Graphs are built syntactically, with no per-package build configuration. [primary-snippet] — [arXiv 2211.01224](https://arxiv.org/pdf/2211.01224); [EVCS listing](https://symposium.eelcovisser.org/details/evcs-papers/11/Stack-graphs-Name-Resolution-at-Scale); [GitHub blog 2021](https://github.blog/open-source/introducing-stack-graphs)
- The github/stack-graphs repository is now archived: "no longer supported or updated by GitHub." [primary-read] — [stack-graphs README](https://github.com/github/stack-graphs/blob/main/README.md)

**Sourcegraph SCIP (successor to LSIF)** [primary-read] — [SCIP DESIGN.md](https://github.com/sourcegraph/scip/blob/main/docs/DESIGN.md)
- SCIP is "a *transmission* format… not… a *storage* format for querying." Stated non-goal: "Support efficient code navigation by itself. Why: Code navigation fundamentally requires some form of **bidirectional lookup which is best served by a query engine**."
- Goals include "file-level incrementality" and parallel indexers "for large monorepos". It avoids direct graph encoding because whole-graph indexers "are less likely to… support parallelism" and need a lot of memory.
- Integer IDs were avoided: "With LSIF, we've had off-by-one bugs in indexers cause code navigation to fail repo-wide." LSIF support "has since been fully deprecated and removed." SCIP compresses to roughly 10–20% of its raw size.
- scip-clang is listed as the C/C++ indexer. — [SCIP README](https://github.com/sourcegraph/scip/blob/main/README.md)

**clangd's own index (the system ours is derived from)** [primary-read]
- **Dex** is an "In-memory Dex trigram-based index". It uses query iterators over posting lists of "search tokens, such as fuzzy matching trigrams, scopes, types". Trade-off: "While consuming more memory and having longer build stage due to preprocessing, Dex will have substantially lower latency." — [clangd Dex.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/dex/Dex.h)
- Trigrams are generated from the *unqualified* symbol name by segment. For "FooBar": `{f, fo, fb, foo, fob, fba, oob, oba, bar}`. They are lowercase and de-duplicated. A query matches if query trigrams ⊆ symbol trigrams, and short queries use prefix trigrams. — [clangd Trigram.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/dex/Trigram.h)
- Posting lists are VByte-compressed in chunks: "Compression saves memory at a small cost in access time." — [clangd PostingList.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/dex/PostingList.h)
- Each Symbol carries a precomputed popularity count: "`unsigned References` — The number of translation units that reference this symbol from their main file. This number is only meaningful if aggregated in an index." — [clangd Symbol.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Symbol.h)
- **MergedIndex**: "the Dynamic index covers few files, but is relatively up-to-date. The Static index covers a bigger set of files, but is relatively stale." For refs: "We consider the dynamic index authoritative and report all its refs, and only report static index refs from other files". Results stream under `Req.Limit` and return a `More` flag. — [clangd Merge.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Merge.h); [clangd Merge.cpp](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Merge.cpp)
- `RefsRequest` has an optional `Limit`: "If set, limit the number of refers returned from the index." — [clangd Index.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Index.h)
- clangd ships with defaults `--limit-references` = **1000** ("Limit the number of references returned by clangd. 0 means no limit") and `--limit-results` = **100**. — [clangd ClangdMain.cpp](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/tool/ClangdMain.cpp)

### Inferences
- **Hot-symbol references.** Every production system precomputes and ranks. Google optimizes the merged xref graph "for the most common queries" and ranks by priority-ordered shards, fetching everything only on request. Glean stores derived predicates. clangd stores a per-symbol reference count and caps references at 1000 by default. For us, the precedent is (a) persisted per-symbol counts and grouped aggregates (refs per file/module, per kind), (b) a default limit with a total count and a `more`/truncated flag, and (c) "complete" mode as an explicit opt-in.
- **Leading-wildcard substring search.** clangd's own design answer is a trigram inverted index over unqualified names, and Google and GitHub generalize it to n-grams. Precedent strongly favors an n-gram/trigram index over full scans. One caveat from the literature: trigrams have false candidates and need a verification pass, and very short or very common patterns still need result caps.
- **Project + engine merge.** Two well-documented patterns exist. clangd's MergedIndex makes the small fresh index authoritative for its files and filters the big index by file ownership, streaming under a limit. Glean's stacked DBs hide excluded units in the base. Both avoid materializing a merged copy. Both depend on cheap per-file ownership checks, and Glean caches these because they are hot.
- SCIP's "a query engine is needed for bidirectional lookup" supports keeping relation tables indexed in both directions (caller→callee and callee→caller, base→derived and derived→base) rather than one direction plus scans.
- Google's "cross-reference index cannot be incremental at scale" lesson argues for treating the engine index as a stable, rarely rebuilt base and making only the project layer incremental. This mirrors Kythe's daily base plus instant text index, and clangd's static plus dynamic split.

### Gaps
- Meta has not published Glean production latency numbers for find-references; the only figures are third-party.
- No published LSIF/SCIP performance evaluation (query latency, index size vs. LSIF) was found beyond the design doc's qualitative points and the 10–20% compression ratio.
- I found no academic paper evaluating stack graphs' performance numbers in the accessible excerpts.
- The Glean Dec 2024 blog body (sections on incremental indexing) could not be read directly.

## Q4. How are references per symbol distributed in large codebases? How many symbols are "hot"?

### Takeaway
Every major study finds heavy-tailed (power-law, Pareto or log-normal) distributions for incoming dependencies, method-call counts and identifier frequencies. Incoming dependencies, the analogue of "references to a symbol", fit power laws best, with density exponents near **2** (about 1.7–2.1). Outgoing dependencies are less skewed. At an exponent near 2, a tiny fraction of symbols, roughly the top 0.1–1%, can hold a majority of all references. So hot-symbol handling is a structural property of large codebases, not an edge case. Google reports that any short substring matches thousands to millions of times, yet about a third of searches have fewer than 20 results. The workload is bimodal: most queries are small, and a few are enormous.

### Cited Findings
- Louridas, Spinellis & Vlachos, "Power Laws in Software", ACM TOSEM 18(1), 2008, art. 2, pp. 1–26. "distributions with long, fat tails in software are much more pervasive than previously established, appearing at various levels of abstraction, in diverse systems and languages". Modules are nodes with edges B→A when B depends on A. Fitted exponents k (in/out) and r² (in/out) [primary-snippet] — [author HTML](https://www.spinellis.gr/pubs/jrnl/2008-TOSEM-PowerLaws/html/LSV08.html); [PDF](https://www2.dmst.aueb.gr/dds/pubs/jrnl/2008-TOSEM-PowerLaws/html/LSV08.pdf):
  - J2SE SDK (13,055): 2.09/3.12, r² .99/.86
  - Eclipse (22,001): 2.02/3.15, r² .99/.87
  - OpenOffice (3,019): 1.93/2.87, r² .99/.94
  - BEA WebLogic (80,095): 2.01/3.52, r² .99/.86
  - CPAN packages (27,895): 1.93/3.70, r² .98/.95
  - Linux libraries (4,047): 1.68/2.56, r² .92/.62
  - FreeBSD libraries (2,682): 1.68/2.56, r² .91/.58 (identical to the Linux row in the snippet, possibly a transcription issue)
  - MS-Windows binaries (1,355): 1.66/3.14, r² .98/.76
  - FreeBSD ports (5,104): 1.75/2.97, r² .94/.76
  - Interpretation: "Some modules, those with a high number of incoming links, tend to be overwhelmingly reused" (winner-takes-all). Incoming fits have higher r² in every row.
- Myers, "Software systems as complex networks", Phys. Rev. E 68, 046116 (2003). It covers C++ class collaboration graphs (VTK, Digital Material, AbiWord) and C call graphs (e.g., MySQL, XMMS), and reports heavy-tailed in- and out-degree distributions P(k) ~ k^−γ. A review reports the out-degree exponent is higher than the in-degree one, meaning incoming links are more skewed. Exact γ values were not retrieved. [primary-snippet / secondary] — [arXiv cond-mat/0305575](https://arxiv.org/pdf/cond-mat/0305575); [Cornell copy](https://www.cac.cornell.edu/myers/papers/Myers2003_softwarenet.pdf); [review arXiv 1608.01533](https://arxiv.org/pdf/1608.01533)
- Concas, Marchesi, Pinna & Serra, "Power-Laws in a Large Object-Oriented Software System", IEEE TSE 33(10):687–708 (2007). Ten properties of a Smalltalk system, including names of variables and methods, method calls, and class-graph in- and out-degree, are "mostly Pareto, with some log-normal". A Yule (preferential-attachment) process reproduces several of them. "The usual evaluation of systems based on mean and standard deviation of metrics can be misleading." [primary-snippet] — [TSE bib entry](https://ftp.math.utah.edu/pub/tex/bib/idx/ieeetranssoftweng2000/33/10/687_708.html); [UniCa IRIS](https://iris.unica.it/handle/11584/97750)
- Baxter et al., "Understanding the Shape of Java Software", OOPSLA 2006, pp. 397–412: "some relationships follow power-laws, while others do not". Related work on 12 Java applications found in-degree fits power laws well while out-degree is curved, closer to exponential. [primary-snippet / secondary] — [Auckland repository](https://researchspace.auckland.ac.nz/handle/2292/16834?show=full); [arXiv 0802.2306](https://arxiv.org/pdf/0802.2306)
- Vasa, Lumpe, Branch & Nierstrasz, "Comparative Analysis of Evolving Software Systems Using the Gini Coefficient", ICSM 2009, pp. 179–188. Many metrics "are distributed like wealth, with high concentrations of values in selected locations". Gini values were "remarkably high" and stable across releases for Java and C# systems. [primary-snippet / secondary] — [BORIS Bern](https://boris.unibe.ch/37171); [review arXiv 1608.01533](https://arxiv.org/pdf/1608.01533)
- Identifier and token frequency follows Zipf–Mandelbrot. Pierret & Poshyvanyk (ICPC 2009) found good fits across OO, imperative, functional and markup languages. An APSEC 2022 study found Java names "close to Zipf's law", with frequent names shorter. [primary-snippet] — [Pierret & Poshyvanyk ICPC 2009](https://www.cs.wm.edu/~denys/pubs/ICPC2009_PiePos.pdf); [APSEC 2022 names study (HUJI; author list not verified)](https://www.cse.huji.ac.il/~feit/papers/NameVoc2022APSEC.pdf)
- Library-routine reuse counts on Unix shared objects agree with Zipf-style c·n^−1 laws. [primary-snippet] — [arXiv cs/0508023](https://arxiv.org/pdf/cs/0508023)
- Google: "any short substring will occur thousands, if not millions, of times", and "about one-third of user searches have fewer than 20 results". [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)
- Google SWE book on code style: a browsable codebase favours "using named types rather than generic things like strings or integers, because it's then easy to find all usages" (footnote 4). It implicitly acknowledges that ubiquitous primitive types (our `int32`, `FString`) are degenerate find-usages targets. [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)

### Inferences
- **How many symbols are hot (computed by me; illustrative, not from a source).** Take a continuous Pareto density with exponent α, so tail index a = α−1. The share of all references held by the top fraction p of symbols is p^(1−1/a). With the in-degree exponents above:
  - α = 2.1: top 0.1% ≈ 53%, top 1% ≈ 66%, top 5% ≈ 76% of all references.
  - α = 2.3: top 0.1% ≈ 20%, top 1% ≈ 35%, top 5% ≈ 50%.
  - α = 2.5: top 0.1% ≈ 10%, top 1% ≈ 22%, top 5% ≈ 37%.
  - A finite simulation (N = 1M symbols, α = 2.0) gave median refs = 2, mean ≈ 14, max ≈ 1.9M, with the top 1% holding ≈ 71% of refs.
  - Implication: per-symbol cost is tiny for the median symbol, while the **top ~0.1–1% of symbols (hundreds to a few thousand in an engine-scale index) can account for most of the reference rows**. Cost is dominated by the maximum, not the mean. That is why "average latency" looks fine while specific queries (`check`, `TEXT`, `FString`, `UObject`, `int32`) blow up.
  - Caveat: Louridas et al. measured module- and class-level dependencies, not symbol-level references in C++. Macros and builtin typedefs like `int32` are likely even more extreme outliers than class dependencies. This should be validated directly on our index (rank-frequency plot of refs per symbol).
- Because the distribution is stable across releases (Vasa et al.) and the generating process is preferential attachment (Concas et al.), the hot set is predictable and stable. Precomputing or caching aggregates for a fixed hot set (by reference count, refreshed at index build) is a sound strategy, not a moving target.

### Gaps
- I found **no published per-symbol reference-count distribution for a C++ codebase** (let alone Unreal Engine) at symbol granularity, including macros. The closest are class or module dependency graphs (Myers for C++ class graphs; Louridas for libraries and classes).
- The exact γ values from Myers (2003) Fig. 3 and the per-metric Gini values from Vasa et al. (2009) were not retrievable.
- The literature disagrees on whether out-degree follows a power law or is exponential. This matters less for us, because references to a symbol are in-degree.

## Q5. What helps LLM agents navigate repositories: structured tools, truncation/ranking, latency and cost?

### Takeaway
Agent-facing interface design matters as much as model choice. SWE-agent showed that **summarized search output capped at about 50 results** (100 in the shipped code) beats both iterative paging and raw shell. Iterative search was *worse than no search tool*. Structure-aware retrieval (AST-level search APIs in AutoCodeRover; code graphs in RepoGraph and LocAgent; hierarchical file→function→line localization in Agentless) improves localization and cost. Unbounded graph traversal can blow up cost. The first controlled 2026 study of LSP tools for agents found semantic reference-finding raises **precision** (1.00 vs 0.76 for grep) but costs **more tokens** for strong models, and does not raise recall. Location-only results are worse than results with inline line context. Long, unranked outputs also hurt because models attend poorly to the middle of long contexts.

### Cited Findings
**SWE-agent (Yang et al., NeurIPS 2024; arXiv 2405.15793)**
- With GPT-4 Turbo, SWE-agent resolves 12.47% (286/2,294) of full SWE-bench and 18.00% (54/300) of Lite, a "64% relative increase compared to Shell-only". [primary-snippet] — [arXiv 2405.15793](https://arxiv.org/pdf/2405.15793); [NeurIPS 2024 paper](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)
- Search ablation (GPT-4 Turbo, Lite): **summarized search 18.0%**, **iterative search 12.0% (−6.0)**, **no specialized search/shell 15.7% (−2.3)**. "Iterative search surprisingly underperforms having no search tool at all." Iterative search "show[s] results one at a time, directly inspired by… Vim or VSCode", and this "can exhaust an agent's cost budget or context window." Summarized search "shows an exhaustive list of search results and provides guidance on refining under-specified queries." The guardrail is "curbing the number of search results to **50 or fewer**". [primary-snippet via search summary; Table 3 not directly verified] — [arXiv 2405.15793](https://arxiv.org/pdf/2405.15793)
- In the shipped tool code, `search_dir` returns **per-file match counts, not lines**. If more than 100 files match it prints "More than N files matched… Please narrow your search." `search_file` refuses when more than 100 lines match. [primary-read] — [SWE-agent tools/search/bin/search_dir](https://github.com/SWE-agent/SWE-agent/blob/main/tools/search/bin/search_dir); [v0.7.0 config/commands/search.sh](https://github.com/SWE-agent/SWE-agent/blob/v0.7.0/config/commands/search.sh)

[secondary, unverified against Table 3] — [Bean Labs research log](https://beancount.io/bean-labs/research-logs/2026/05/01/swe-agent-agent-computer-interfaces-automated-software-engineering)
- "Some exploration patterns (e.g., chains of cd, ls, cat) are extremely inefficient." [primary-snippet] — [arXiv 2405.15793](https://arxiv.org/pdf/2405.15793)

[primary-read README / primary-snippet] — [AutoCodeRover README](https://github.com/AutoCodeRoverSG/auto-code-rover/blob/main/README.md); [arXiv 2404.05427](https://arxiv.org/abs/2404.05427v3)

Plugged into four frameworks, it gave an "average relative improvement of **32.8%**", and "Performance gain… does not rely on more costs." [primary-snippet] — [ICLR 2025 proceedings](https://proceedings.iclr.cc/paper_files/paper/2025/hash/4a4a3c197deac042461c677219efd36c-Abstract-Conference.html); [RepoGraph README](https://github.com/ozyyshr/RepoGraph/blob/main/README.md)

**Why ranking and truncation matter for LLMs**
- Liu et al., "Lost in the Middle: How Language Models Use Long Contexts", TACL 12:157–173 (2024). Performance is U-shaped by the position of relevant information and "can degrade significantly when changing the position of relevant information", even for long-context models. [primary-snippet] — [ACL Anthology](https://aclanthology.org/2024.tacl-1.9/)
- Token use on the same task can vary by up to 30× across runs, and higher token usage does not mean higher accuracy. [secondary] — [How Do Coding Agents Spend Your Money?](https://longjubai.github.io/agent_token_consumption/)

### Inferences
- For agent-facing reference and caller queries on hot symbols, the evidence points to a **summarized, capped, ranked** response:
  - a total count;
  - per-file or per-module grouped counts (SWE-agent's `search_dir` format);
  - the top-N most relevant sites **with one line of code context each** (AgentConnect, 2608.13568);
  - an explicit "narrow your query" hint or a paging and filter option when truncated (SWE-agent).
  This should not be a raw dump of tens of thousands of rows, and not one-at-a-time paging.
- The 2026 study's main gain from semantic references was **precision** (no false call sites), which grep cannot match for overloaded C++ names, macros and templates. Its main failure was **recall**. Our index should therefore (a) say explicitly when results are truncated, with true totals, and (b) offer an exhaustive mode, as Google Code Search does, for refactoring or impact use cases.
- LocAgent's runaway costs from unbounded traversal argue for **hard bounds** on our "impact" and multi-hop caller queries: depth limit, fan-out cap, and stopping at hot nodes such as `check`/`UObject`, whose expansion is uninformative.
- Since agents mostly prefer grep for localization, speeding up substring symbol search mainly benefits the human webview and agents that are explicitly prompted to use it. Fixing hot-symbol reference aggregation benefits both audiences.

### Gaps
- I could not verify SWE-agent Table 3's exact per-row values (30-line vs 100-line vs full-file viewer) from the primary PDF. The 50-result cap is quoted from the paper via search excerpt, while the shipped code uses 100.
- arXiv 2608.13568 is a small preliminary preprint (author byline not confirmed; possibly Pengcheng Xu per a secondary article). No large-scale, peer-reviewed study of LSP or semantic-index tools for agents on C++ was found.
- No study isolates the effect of navigation-tool *latency* (as opposed to output design) on agent success or cost.
- OpenHands-specific findings on navigation tools were not retrieved.

## Q6. Implications: what should be prioritized for our engine-scale index (developers + agents)?

### Takeaway
The literature points to the following order. (1) Fix **hot-symbol reference and caller aggregation** with precomputed counts plus a ranked, capped, grouped response, and an explicit truncation flag and exhaustive mode. This is the largest query class (how/usage examples, where/all-usages, reachability) and is structurally heavy-tailed. (2) Make the **project-over-engine merge** a streaming, file-ownership-shadowed query under a limit (clangd MergedIndex and Glean stacking patterns) rather than a full merge. (3) Add a **trigram/n-gram index** for leading-wildcard symbol search, mainly for the webview's sub-200 ms budget. For agents, optimize **output shape** (summaries, line context, caps) before shaving milliseconds.

### Cited Findings
- "How" (about one third) and "Where" (about 16%, including "all usages of an API") intents, plus call-hierarchy browsing for "What" (about one quarter), are the bulk of code-search use. [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)
- Target sub-200 ms end-to-end for frequent operations; the median server-side search at Google is under 50 ms. [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)
- Ranked search is the common case, with all-results fetched on request through priority-ordered shards. [primary-read] — [SWE book ch.17](https://abseil.io/resources/swe-book/html/ch17.html)
- clangd defaults to `--limit-references=1000` and `--limit-results=100`, stores a per-symbol `References` count, and merges dynamic and static indexes by making the dynamic index authoritative for its files. [primary-read] — [ClangdMain.cpp](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/tool/ClangdMain.cpp); [Symbol.h](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Symbol.h); [Merge.cpp](https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clangd/index/Merge.cpp)
- Glean uses stacked incremental DBs with per-unit exclusion and stored derived facts. [primary-read] — [Glean incrementality doc](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/implementation/incrementality.md)
- Incoming-dependency distributions follow power laws with exponent about 2. [primary-snippet] — [Louridas et al. 2008](https://www.spinellis.gr/pubs/jrnl/2008-TOSEM-PowerLaws/html/LSV08.html)
- For agents, summarized search beats iterative search and no search, and results are capped at about 50. [primary-snippet] — [SWE-agent](https://arxiv.org/pdf/2405.15793)
- LSP references are precise but not cheaper, and line context helps. [primary-snippet / secondary] — [arXiv 2608.13568](https://arxiv.org/abs/2608.13568); [AgentConnect](https://www.agentconnect.md/blog/grep-beat-lsp-harness/)
- Unbounded graph traversal drove LocAgent's runaway cost in a competitor's re-run. [primary-snippet] — [arXiv 2605.17965](https://arxiv.org/pdf/2605.17965)

### Inferences
1. **Hot-symbol references and callers (highest priority, both audiences).** Precompute per-symbol totals and grouped aggregates (by file, module/plugin, and reference kind) at index build. That covers the top ~0.1–1% of symbols by reference count, or all symbols if cheap. The default response should be total + groups + top-N sites with line text + a `truncated`/`more` flag, and the full list only on request or with filters (path, kind, container). This mirrors Google's ranked-default/complete-on-demand split, clangd's 1000-ref limit with a `More` flag, and SWE-agent's summarized search. It turns the worst case from O(refs), up to millions, into O(1) for counts plus O(N) for the shown top-N.
2. **Ranking within references.** For the "how to use this API" intent, rank sites by signals such as being in project code before engine code, file priority or popularity, and diversity across files. Google uses reference-based file priority. Returning the first 1000 rows in storage order is low value.
3. **Bound impact and multi-hop queries.** Use a depth limit, a fan-out cap, and stop-expansion at hot nodes, reporting "N more via `check`". This guards against the GitHub hot-shard and LocAgent unbounded-traversal failure modes.
4. **Project + engine merge.** Query the small project DB first (authoritative for its files), then stream from the engine DB while skipping files the project covers, stopping at the limit (clangd MergedIndex). Treat the engine DB as a stable, rarely rebuilt base, as with Kythe's daily index and Glean's base DB. Avoid materializing merged result sets for hot symbols.
5. **Leading-wildcard substring search.** Use a trigram or n-gram posting index over unqualified symbol names (clangd Dex, Cox, GitHub, Google), with candidate verification and a result cap. Priority is medium: it matters for the webview's 200 ms budget, while agents mostly grep for localization.
6. **Latency targets.** Webview: p95 at or under 200 ms per click, so about 50 ms or less per query when 3–5 run per click. Agent CLI: keep tail latency for hot symbols well under 1 s and measure process startup. Beyond that, token-efficient output beats milliseconds.
7. **Measure our own distribution.** Plot a rank-frequency (log-log) chart of refs per symbol in the engine and project indexes to confirm the heavy tail and size the hot set before choosing a precomputation threshold.

# 구조 점검 — 요청 없이 개선 후보 찾기

> 일부를 Matt Pocock 의 skills(`improve-codebase-architecture`, MIT, Copyright (c) 2026 Matt Pocock)에서 빌려 게임 프로젝트에 맞게 고쳤다.
> 라이선스: `docs/third_party/mattpocock-skills-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

- 쓸 때: 기능 없이 "구조 개선할 곳 찾아줘" · "리팩터링 후보" · "이 시스템 정리하고 싶다".
- 구현하지 않는다. 후보와 근거를 내고 멈춘다.
- 얕다: 호출하는 쪽이 알아야 할 것이 구현만큼 많다. 깊다: 작은 인터페이스 뒤에 동작이 많다.
- locality: 변경 · 버그 · 지식이 한곳에 모인다. leverage: 구현 하나를 호출 N곳 · 테스트 M개가 쓴다.

## 1. 범위를 먼저 정한다 (YAGNI)

안 바뀌는 곳은 깊게 해도 이득이 없다. 자주 바뀌는 곳이 먼저다.
- 사용자가 영역을 말했으면 그것을 쓰고 이력 추론은 건너뛴다.
- 없으면 소스 저장소를 확정하고 hotspot 과 co-change 를 본다.
  - `python ~/.claude/skills/game-architecture/scripts/evidence.py roots`
  - `python ~/.claude/skills/game-architecture/scripts/evidence.py hotspots --path <소스저장소>`
  - `python ~/.claude/skills/game-architecture/scripts/evidence.py coupling --path <소스저장소>`
- 상위가 흩어져 안 보이면 `--months` 로 넓힌다. 커밋이 수십 개 미만이면 근거 세기 상한은 '볼 만함'.
- 용어집 · 결정 기록 · 위키가 있으면 범위 안 쪽을 먼저 읽는다. 읽기만 한다.

## 2. 탐색 (읽기 전용, 출력이 크면 서브에이전트)

규칙대로 훑지 않고, 읽다 마찰이 느껴지는 곳을 적는다. 눈에 띄는 모양:

| 징후 | 게임에서의 모양 | 확인 | 그림 형식 |
|---|---|---|---|
| 개념 하나가 작은 클래스 · BP 여럿에 흩어짐 | 피격 하나에 BP 6개 · 컴포넌트 3개 | 호출을 따라 파일 수를 센다 | architecture-delta |
| 얕은 모듈 | `Super` 만 부르는 매니저, 인터페이스 ≈ 구현 | 지우기 시험 | architecture-delta |
| 종류별 분기 반복 | 캐릭터 · 무기 타입 `switch` 가 여러 파일에 | 타입 이름 grep, 파일 수 | er · uml-class |
| 숨은 결합 | co-change 높은데 include · 모듈 의존 없음 | `coupling` 과 정적 의존 대조 | dependency |
| PIE 로만 시험됨 | 계산은 단위 시험, 버그는 호출 순서에 | 시험 위치 (`game-testing`) | sequence |
| BP/C++ 경계가 샘 | 같은 규칙이 C++ 와 BP 에 둘 다 | BP 에서 같은 판정을 찾는다 | layers |

- 지우기 시험: 층을 지웠다고 쳐 본다. 복잡함이 여러 곳으로 퍼지면 값을 하는 층이다. 그냥 사라지면 전달만 하는 층이라 후보다.
- '바꾸면' 에 새 경계(seam)를 적을 땐 구현체가 하나뿐이면 가짜다. 갈리는 구현이 둘 이상인지 본다.

## 3. 보고 — 후보 표 하나

- 파일: `<프로젝트>/Saved/ClaudeArch/<YYYYMMDD>-구조점검.md` (Unity 는 `Library/ClaudeArch/`)
- 렌더: `python ~/.claude/skills/game-architecture/scripts/render.py <파일.md> --open`
- 원본의 Tailwind HTML 은 쓰지 않는다. 후보 절 제목은 `## 선택지` 로 시작해야 렌더러가 접는다.
- 후보는 5개 이하, 한 행에 하나, 근거 센 순서. 카드나 줄글 설명을 붙이지 않는다.
- 근거 세기: 강함 = hotspot 상위 + 땜질 흔적 + 코드로 확인 / 볼 만함 = 신호 하나나 코드만 / 추측 = 읽은 인상뿐
- 표 아래 `추천: <후보> — <이유 한 줄>`. 기준은 다음 요청 때 고칠 곳이 주는 폭이다. 고르는 것은 사용자다.
- 결정 기록과 어긋나는 후보는 마찰이 실제일 때만 올리고 문제 칸에 `⚠ 결정 기록 <이름> 과 충돌` 로 표시한다.
- Before/After 는 1–2개 후보만. 표의 '그림 형식' 은 출발점이고 '바뀌는 것' 으로 확정한다 (`diagram-types.md`).
  - 그림 절 첫 줄: `바뀌는 것: <한 줄> → <형식>`
  - 파일: `<YYYYMMDD>-구조점검-구조-후보<번호>-<형식>[-전|-후].html` (diagram-design 이 없으면 SKILL.md §4 의 Mermaid)
- 읽기 규칙(SKILL.md): 첫 화면 30줄 이하, 한 줄 120자 이하, 파일:줄 · 수치는 '근거' 절.

## 4. 멈춘다

- 인터페이스 안은 아직 내지 않는다. 어느 후보를 더 볼지 묻고 멈춘다.
- 사용자가 후보를 고르면 그것을 요청으로 SKILL.md 1단계(축 분해)부터 간다.
- 근거 있는 거절은 결정 기록 후보라고 한 줄만 알린다. 파일은 쓰지 않는다.

## 선택지 — 후보 N개

| 1 | <용어집 말로> | <경로> | <한 구절> | <한 구절> | locality · leverage · 테스트 | 강함 |

### 신호

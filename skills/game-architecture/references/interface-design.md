# 인터페이스 설계 — 고른 구조를 깊게

> 일부를 Matt Pocock 의 skills(`codebase-design`, MIT, Copyright (c) 2026 Matt Pocock)에서 빌려 게임 프로젝트에 맞게 고쳤다.
> 라이선스: `docs/third_party/mattpocock-skills-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

## 쓸 때

- 사용자가 선택지 B·C 를 골랐고 인터페이스 모양(깊이, 경계 위치, 노출할 것)이 열려 있을 때 구현 전에 연다.
- 인터페이스가 정해졌거나 한 모듈 안의 변경이면 "정해져 있어 건너뜀" 한 줄만 적고 SKILL.md 5절 2단계(계획)로 간다.
- 4절(서브에이전트 3~4번)은 두 모듈 이상에 걸칠 때만.

## 1. 말

| 말 | 뜻 |
|---|---|
| 모듈 | 인터페이스와 구현을 가진 모든 것. 함수부터 서브시스템, asmdef 까지 |
| 인터페이스 | 호출하는 쪽이 알아야 하는 전부. 시그니처 + 불변식, 호출 순서, 실패 모드, 필요한 설정, 성능 특성 |
| 깊이 | 인터페이스 하나로 쓸 수 있는 동작의 양. 많을수록 깊다 |
| 경계(seam) | 그 자리에서 코드를 고치지 않고 동작을 바꿀 수 있는 곳. 인터페이스가 놓이는 위치 |
| 어댑터 | 경계에서 인터페이스를 채우는 구체물. 내용이 아니라 맡은 역할 |
| leverage | 호출하는 쪽이 얻는 것. 배운 인터페이스 대비 얻는 동작 |
| locality | 고치는 쪽이 얻는 것. 변경, 버그, 검증이 한곳에 모인다 |

- 프로젝트 용어집(GLOSSARY.md 등)이 있으면 도메인 사물 이름은 그 말이 이긴다. 이 표는 구조 말만.
- '컴포넌트'는 엔진 말(ActorComponent, MonoBehaviour)이다. 구조를 말할 때는 '모듈'로 쓴다.

## 2. 원칙

- 지우기 시험: 모듈을 지웠다고 쳐 본다. 복잡함이 호출하는 곳 여러 군데로 퍼지면 값을 하는 모듈이다.
  - 그냥 사라지면 전달만 하는 층이다. 피해 파이프라인의 결과 전달 층이 그렇다.
- 인터페이스가 테스트 면이다. 호출하는 쪽과 테스트가 같은 경계를 지난다.
  - 상호작용 시스템은 `TryInteract` 로 테스트한다. 후보 수집 함수를 찌르고 싶으면 모듈 모양이 틀린 것이다.
- 어댑터가 하나면 가짜 경계, 둘이면 진짜 경계다.
  - SO 이벤트 채널은 구독자가 하나뿐이면 가짜다. 직접 호출이 낫다.
  - GAS Ability 는 발동 조건, 비용, 쿨다운, 태그가 이미 있다. 같은 일을 하는 층을 위에 얹지 않는다.
- 깊이는 인터페이스의 성질이다. 안쪽이 작은 부품 여럿이어도 깊을 수 있다.
  - Subsystem 하나 뒤에 Component 여럿이 있어도 함수 하나만 알면 되면 깊다. getter 전달만 하면 얕다.
  - 안쪽 경계는 비공개로 둔다. 테스트가 쓴다고 인터페이스로 올리지 않는다.

깊은 호출 예. 순서와 실패 처리는 경계 뒤에 있다.

```cpp
// UE 피해 파이프라인: 호출부는 결과만 안다
FDamageResult R = GetWorld()->GetSubsystem<UDamageSubsystem>()->Apply(
    FDamageRequest{Attacker, Target, Hit});
```

```csharp
// Unity 상호작용: 후보 수집과 조건은 안에 있다
InteractResult r = interaction.TryInteract(player);
if (r.Failed) ShowHint(r.Reason);
```

## 3. 의존 4종류

| 종류 | 게임 예 | 테스트 방법 |
|---|---|---|
| 같은 프로세스 | 피해 공식, 규칙 판정, 쿨다운 계산 | 모듈을 합쳐 인터페이스로 직접. 어댑터 없음 |
| 로컬 대체 가능 | 엔진 서브시스템, 에셋 로딩, 타이머 | 테스트 월드, 테스트용 SO 로 돌린다. 경계는 안쪽 |
| 원격이지만 우리 것 | 전용 서버, 자체 백엔드 | 포트 + 실서버 어댑터 + 메모리 어댑터 (ports & adapters) |
| 진짜 외부 | 플랫폼 SDK, 결제, 업적 | 포트로 주입받고 테스트에서는 목 어댑터 |

- 갈아끼운다, 겹치지 않는다: 깊어진 인터페이스에 테스트가 생기면 얕은 모듈의 옛 단위 테스트는 지운다.
- 테스트 규칙 전체: [good-tests.md](../../game-testing/references/good-tests.md)

## 4. 두 번 설계

### 4-1. 문제를 사용자에게 먼저 적는다

- 인터페이스가 만족해야 할 제약
- 기댈 의존과 그 종류(3절)
- 제약을 구체로 보이는 스케치 (제안 아님)
- 적자마자 4-2 로 간다. 사용자가 읽는 동안 서브에이전트가 일한다

### 4-2. 서브에이전트를 병렬로 (Agent 도구, 한 메시지에 여러 호출)

- 안1 진입점 최소: 진입점 1~3개, 진입점당 leverage 최대
- 안2 유연성 최대: 많은 용례와 확장을 받는다
- 안3 가장 흔한 호출을 가장 쉽게: 기본 경우가 한 줄이다
- 안4(선택) ports & adapters: 3절 셋째·넷째 의존이 있을 때만
- 브리프에 넣을 것: 파일 경로, 결합, 의존 종류, 경계 뒤에 있는 것, 이 문서와 용어집의 말
- 비용: `model: sonnet`, 파일 수정 금지, 안당 25줄 이내

각 안이 돌려줄 것:

1. 인터페이스: 타입, 함수 + 불변식, 호출 순서, 실패 모드
2. 호출 예: UE 는 C++, Unity 는 C#
3. 경계 뒤에 숨는 것
4. 의존 전략과 어댑터
5. 트레이드오프: leverage 가 높은 곳, 얇은 곳

### 4-3. 견주고 추천한다

안을 차례로 보여 준 뒤 표 하나로 견준다.

| 안 | 깊이 | locality | 경계 위치 | 다음 요청 때 고칠 곳 |
|---|---|---|---|---|
| 1 최소 | … | … | … | … |
| 2 유연 | … | … | … | … |
| 3 흔한 호출 | … | … | … | … |
| 4 포트(선택) | … | … | … | … |

- 마지막 줄: `추천: <안> — <이유 한 줄>`. 안을 섞어도 된다.
- 고르는 것은 사용자다. 구현 없이 멈춘다. 고르면 5절 2단계로 간다 (검증 기준 먼저, `game-testing`).

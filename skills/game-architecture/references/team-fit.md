# 프로젝트의 컨벤션에 맞춘다 — 선례 · 팀 피드백 로그 · 납득 검사

구조가 좋은지는 내 눈이 아니라 그 프로젝트의 사람들이 정한다. 다른 프로그래머가 읽고, 기획자가 세팅한다.
모델은 사용자의 전제에 맞춰 답하는 쪽으로 기운다. 그래서 사용자의 시각이 걸러지지 않고 커진다.
아래 세 가지로 기준점을 사용자에서 프로젝트로 옮긴다. 근거와 출처는 하네스 `docs/VERIFICATION.md` 의 '프로젝트의 컨벤션에 맞추기'.

## 0. 우선순위

1. 프로젝트 선례 — 다른 사람이 같은 종류를 실제로 넣은 방식.
2. 팀 피드백 로그 — 이 프로젝트에서 받은 지적.
3. 사용자 개인 규칙과 내 취향 — 프로젝트가 정하지 않은 곳에만.

위가 아래를 이긴다. 벗어날 때는 이유를 선택지 표의 근거 칸에 적는다.

## 1. 선례 먼저

구조를 내기 전에 같은 종류를 이 프로젝트에서 누가 어떻게 넣어 왔는지 본다.

- `python ~/.claude/skills/game-architecture/scripts/evidence.py precedent <경로 조각> --path <소스 저장소>`
  넣은 커밋 · 넣은 사람 · 그때 같이 바뀐 곳이 나온다. git 과 svn 둘 다 된다. 내 이름을 못 맞히면 `--me <이름>`.
- 최근 선례 한두 개는 파일을 직접 연다. 이름 짓기, 데이터를 두는 곳, 등록하는 곳, 기획자가 만지는 곳을 본다.
- 선례의 패턴을 따르는 안을 선택지 표의 한 행으로 반드시 넣는다. 벗어나는 안은 '벗어나는 이유'를 근거 칸에 적는다.
- 선례가 전부 사용자 것이면 팀의 컨벤션이라고 쓰지 않는다. 기존 파일을 직접 읽거나 팀의 방식을 사용자에게 묻는다.
- 이력이 없으면(저장소 없음 · 새 프로젝트) 같은 종류의 기존 파일 두세 개를 읽어 패턴을 적는다.

## 2. 팀 피드백 로그

동료의 지적으로 방향이 바뀐 일을 적어 두고 다음에 먼저 읽는다. 쓰는 것은 선택이다. 파일이 없으면 이 절은 건너뛴다.

- 위치: `<프로젝트>/.claude/team_feedback.md`. 커밋하지 않는다. 회사 저장소에 올리지 않는다.
- 적는 때: 사용자가 "리뷰에서 지적받았다", "다른 사람이 이 구조는 아니라고 했다"처럼 말할 때. 코드 리뷰 기록이 없는 저장소(svn)에서는 사용자의 말이 유일한 출처다.
- 모르는 칸은 지어내지 않는다. 사용자에게 한 번 묻고, 그래도 모르면 `모름` 으로 둔다.
- 항목은 덧붙이기만 한다. 요약해서 다시 쓰지 않는다. 틀린 것으로 드러난 항목은 지우지 않고 `뒤집힘: <이유>` 한 줄을 단다.
- 읽는 때: 구조 선택지를 내기 전. 이번 요청과 종류가 같은 항목만 근거로 쓴다. 다른 프로젝트의 피드백 로그는 가져오지 않는다.

```
## <날짜> · <무엇에 대한 지적: 데이터 구조 · 클래스 경계 · 세팅 방식 …>
- 누가: <동료 프로그래머 | 기획자 | 리드 …>
- 상황: <무엇을 만들고 있었나>
- 내가 낸 것: <한 줄>
- 팀이 고른 것: <한 줄>
- 이유: <그쪽이 든 이유. 모르면 모름>
- 다음에 볼 것: <같은 종류를 만나면 먼저 확인할 것 한 줄>
```

## 3. 납득 검사

반대 검토(critique.md)의 비판자에게 선례 출력과 피드백 로그 항목을 넘기고, 검수 항목에 '납득'을 더한다. 반대 검토를 건너뛰는 작은 변경이면 아래 세 질문에 직접 답해 근거 절에 적는다.

| 질문 | 근거로 댈 것 |
|---|---|
| 이 프로젝트의 다른 프로그래머가 처음 보고 어디에 있는지 찾을 수 있나? | 같은 종류가 있는 폴더 · 이름 규칙 |
| 기획자 · 다른 직군이 세팅할 때 몇 단계인가, 기존 세팅과 같은 방식인가? | 기존 데이터 애셋 · 표의 모양 |
| 선례와 다른 점은 무엇이고, 그 차이를 팀이 받아들일 이유가 있나? | precedent 출력, 피드백 로그 항목 |

근거 없이 "납득된다"고 쓰지 않는다. 근거가 추정뿐이면 사용자에게 팀의 방식을 묻는 질문으로 바꾼다.

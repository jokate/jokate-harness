# 반대 검토 — 누구 안이든 같은 기준으로

> 비판자를 만든 쪽과 떼는 방식은 AWS AI-DLC(`aidlc-workflows` 리뷰어 지식, MIT-0)에서, 질문으로 캐는 방식은 Matt Pocock 의 `grilling`(MIT)에서 왔다.
> 라이선스: `docs/third_party/aidlc-workflows-LICENSE` · `docs/third_party/mattpocock-skills-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

사용자의 판단도, 내 추천도 틀릴 수 있다. 그래서 큰 결정은 누가 낸 안인지 모르는 비판자가 같은 기준으로 판다.
목적은 결정을 내는 것이다. 모든 안을 깎아내리고 끝나면 실패다.

## 0. 쓸 때

- 새 시스템 · 시스템 경계 · 데이터 구조(저장 형식, 네트워크에서 누가 판정하나)를 정하는 선택지일 때.
- 사용자가 직접 구조를 냈을 때("이렇게 짜자", "X 패턴으로 가자").
- 그 밖(한 시스템 안의 구현 방식)은 건너뛰고 구조 문서에 `반대 검토 건너뜀 — <이유>` 한 줄만 쓴다.

## 1. 안을 모은다

- 사용자 안을 그대로 구현하지 않는다. 선택지 표의 한 행으로 넣고 다른 안과 같은 칸을 채운다.
- 사용자 안이 이미 있는 선택지와 같으면 그 행에 합친다.

## 2. 비판자를 따로 띄운다

Agent 도구로 새 서브에이전트 하나. 기본 `model: sonnet`, 사용자가 "중요"라고 하면 `model: opus`. 파일 수정 금지, 700단어 이내.

- 넘기는 것: 요청 축(1절), 안마다 한 줄 + 바뀌는 파일 · 모듈, 기존 확장 지점과 신호(2절), 같은 축 과거 요청, 프로젝트 지향 문서와 용어집 경로.
- 넘기지 않는 것: 누가 낸 안인지, 내 추천, 내 판단 메모. 안은 A · B · C 로만 부르고 추천을 맨 앞에 두지 않는다.
- 지시: "통과는 반박에 실패한 결과다. 안마다 3절 표를 채우고, 4절 질문을 5개 이하로 내고, 마지막에 가장 덜 나쁜 안 하나를 골라라."
- 비판자는 한 번만 띄운다. 두 번째 바퀴도 이때 받은 질문에서 고른다(다시 띄우면 비용이 두 배고, 누가 낸 안인지 아는 내가 답을 옮기게 된다).

## 3. 안마다 오류 가능성을 잰다

검수 항목 여섯 가지. 안마다 해당하는 것만 쓴다.

| 항목 | 묻는 것 |
|---|---|
| 가정 | 기획 · 콘텐츠가 이렇게 갈 거라는 가정이 깨지면? |
| 확장 | 같은 축 요청이 하나 더 오면 몇 곳을 고치나, 땜질인가? |
| 경계 | 누가 소유하고 누가 부르나, 네트워크에서는 누가 판정하나? |
| 데이터 | 저장 형식 · 에셋 참조가 바뀌면 옮기기가 되나? |
| 검증 | 이 안을 자동 테스트로 확인할 수 있나? |
| 지향 | 프로젝트 지향 문서 어느 줄과 맞고 어긋나나? |

비판자 출력 표:

| 안 | 가장 강한 찬성 | 오류 가능성 (항목) | 드러나는 때 | 풀리는 조건 | 근거 |
|---|---|---|---|---|---|
| A | … | 확장: 보스 전용 경직이 오면 3곳을 고친다 | 다음 상태이상 요청 | 상태이상 종류가 2개로 끝난다는 기획 확인 | 확인 |

- 오류 가능성마다 '풀리는 조건'을 쓴다. 무엇을 확인해도 풀리지 않는 비판은 버린다.
- 근거: 확인(코드 · 이력 · 문서로 봄) / 추정. 추정뿐인 오류 가능성은 결론을 바꾸지 못한다.
- 지향 문서 자체가 실패 원인으로 보이면 `지향 재검토 후보` 로 적는다. 지향도 틀릴 수 있다.
- 끝: `가장 덜 나쁜 안: <안> — 이 안이 지는 조건: <한 줄>`. "다 문제가 있다"는 결론이 아니다.

## 4. 질문으로 캔다

비판자는 표와 함께 질문을 낸다. 사용자 판단의 근거와 추천 안의 가정을 같이 캔다.

- 질문은 '질문 쓰는 법'(SKILL.md 3절) 표 형식, 추천 답 칸 포함.
- 답에 따라 고를 안이 바뀌는 질문만 낸다. 안 바뀌면 묻지 않고 표에만 둔다.
- 코드 · 기획서 · 위키로 알 수 있는 것은 묻지 않고 찾는다. 결정과 가정만 묻는다.
- 5개 이하, 고를 안을 많이 바꿀 수 있는 순서로. 1바퀴에 위 3개, 2바퀴에 나머지 중 아직 고를 안을 바꾸는 것만 2개 이하.

## 5. 보여 준다

- 구조 문서 `## 반대 검토` 절(선택지 바로 뒤)과 대화에 같은 표를 낸다. 안 이름을 되살린다: "사용자 안(B)", "추천 안(A)".
- 사용자 안의 약점과 추천 안의 약점을 같은 표에서 같은 크기로 쓴다.
- 표는 안마다 한 행, 칸마다 한 구절. 첫 화면이 30줄을 넘으면(render.py 읽기 점검) 표를 '근거' 절로 내리고 '가장 덜 나쁜 안' 줄만 남긴다.
- 비판자 결론이 내 추천과 다르면 그대로 적는다. 추천을 유지하면 이유 한 줄. 비판자 결과를 내 추천 쪽으로 고쳐 쓰지 않는다.

## 6. 주고받는다 — 두 바퀴까지

- 1바퀴: 비판자 질문 중 위 3개 → 사용자 답 → 답이 바꾼 칸만 표에 반영한다.
- 2바퀴: 남은 질문 중 아직 고를 안을 바꾸는 것만, 2개 이하. 남은 게 없으면 2바퀴는 없다.
- 사용자가 반박하면 새 근거(사실 · 제약 · 기획)가 있을 때만 판단을 바꾸고, 무엇 때문인지 적는다.
  근거 없이 같은 말이 다시 오면 판단을 유지하고 그렇다고 말한다. 밀려서 동의하지 않는다.
- 사용자 근거가 이기면 추천을 거두고 그렇다고 말한다.
- 고른 것은 반박이 아니다. 사용자가 안을 고르면 그 안으로 가고, 내 반대는 8절 남은 반대로 보낸다.

## 7. 끝낸다 — 빙빙 돌지 않게

아래 중 하나면 질문을 멈추고 결정으로 간다(5절 멈춤, 고르는 것은 사용자).
- 두 바퀴가 끝났다.
- 남은 반대가 고를 안을 바꾸지 못한다.
- 남은 반대의 풀리는 조건이 지금 확인할 수 없는 것이다(구현 · 플레이 뒤에만 안다). 이런 반대는 질문 대신 버리는 프로토타입(prototype.md) 제안이나 남은 반대로 보낸다.
- 사용자가 "정했다"고 했다.

같은 반대를 말만 바꿔 다시 올리지 않는다. 정한 것은 새 근거가 생길 때만 다시 연다.

## 8. 남은 반대를 남긴다

- 결정 뒤 풀리지 않은 반대를 구조 문서 `## 반대 검토` 아래 `남은 반대` 에 한 줄씩 적는다: 무엇 · 어떤 요청이 오면 드러나나.
- 위키를 쓰면 5절 5단계에서 그 시스템 쪽에 같이 남긴다.
- 같은 축 요청이 다시 오면 남은 반대를 먼저 꺼내 맞았는지 본다. 맞았으면 다음 반대 검토의 근거로 쓴다.

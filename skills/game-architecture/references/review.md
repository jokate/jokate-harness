# 구현 후 리뷰 — 규칙 축 · 사양 축

> 일부를 Matt Pocock 의 skills(`code-review`, MIT, Copyright (c) 2026 Matt Pocock)에서 빌려 게임 프로젝트에 맞게 고쳤다.
> 라이선스: `docs/third_party/mattpocock-skills-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

사용자가 고른 구조를 구현한 직후에 밟는다. diff 를 한 문장으로 설명할 수 있는 수정이면 건너뛴다.
새 컨텍스트 서브에이전트 둘에게 축별로 따로 맡긴다. 한 축이 통과해도 다른 축이 실패할 수 있어 섞지 않는다.

## 1. 기준점을 고정한다

기준점은 구현 직전의 커밋 · 브랜치 · 태그다. 사용자가 말한 것을 쓰고, 없으면 묻는다.
- git: `git rev-parse <기준>` → `git diff <기준>...HEAD` · `git log <기준>..HEAD --oneline`
- svn: `svn diff -r <기준>:HEAD` · `svn log -r <기준>:HEAD` (기준은 구현 직전 리비전 번호)
- 없는 ref · 빈 diff 는 서브에이전트를 띄우기 전에 여기서 멈춘다.
- `.uasset` · `.umap` · 프리팹은 diff 로 읽히지 않는다. 파일 목록만 넘기고 애셋 쪽은 '검증 안 됨'으로 적는다.

## 2. 사양 출처

찾은 것을 모두 사양 축에 넘긴다.
1. 구조 문서 `Saved/ClaudeArch/<YYYYMMDD>-<주제>.md` (Unity 는 `Library/ClaudeArch/`).
   - 사용자가 고른 선택지 행과 그 행의 '다음 요청 때 고칠 곳' 개수(계획값).
2. 기획서의 해당 절 (`game-design-doc` 사양 표).
3. 구현 전에 적은 검증 기준 (`game-testing`).
4. 셋 다 없으면 사양 축은 "사양 없음" 한 줄로 보고하고 서브에이전트를 띄우지 않는다.

## 3. 규칙 출처

문서에 적힌 규칙을 모은다. 있는 파일은 전부 넣는다.
- 프로젝트 `CLAUDE.md` · `CLAUDE.local.md`
- 코딩 표준 문서 (`CODING_STANDARDS.md`, `CONTRIBUTING.md` 등)
- 프로젝트가 문서로 남긴 엔진 관례 (네이밍 접두사, 모듈 · asmdef 경계, BP 와 C++ 역할 나눔)

그 위에 고정 기준선을 얹는다. Fowler 의 냄새(smell) 12개이고 change amplification 과 직결된다.
- 저장소 규칙이 항상 이긴다. 규칙이 허용한 것은 냄새로 치지 않는다.
- 냄새는 늘 판단이다. "~일 수 있음"으로 쓴다. 린터 · 컴파일러 · UHT 가 잡는 것은 뺀다.

각 줄은 무엇 → 고치는 법이다. 앞의 셋을 먼저 본다.
- Repeated Switches: 캐릭터 · 무기 종류마다 같은 `switch`/`if` 가 반복(땜질 신호) → 다형성, 또는 DataAsset · 맵 한 곳.
- Shotgun Surgery: 요청 하나에 여러 파일을 고침(change amplification) → 같이 바뀌는 것을 한 모듈로.
- Speculative Generality: 같은 축 요청 증거가 2건 미만인데 추상화 · 훅 · 파라미터 → 지우고 인라인으로.
- Middle Man: 전달만 하는 매니저 · 서브시스템 → 없애고 실제 대상을 직접 부른다.
- Feature Envy: 제 데이터보다 남의 데이터를 더 만지는 함수 → 그 데이터가 있는 클래스로 옮긴다.
- Data Clumps: 같이 다니는 파라미터(Damage, Instigator, HitResult…) → 구조체나 DataAsset 하나로.
- Primitive Obsession: `FName` · `FString` · `int` 로 쓴 도메인 개념 → GameplayTag · enum · 구조체.
- Divergent Change: 한 클래스를 무관한 이유로 고침(Character 에 입력 · 전투 · UI) → 이유별 컴포넌트로 분리.
- Refused Bequest: 파생 BP 가 부모 함수 대부분을 덮어씀 → 상속을 버리고 컴포넌트 조합으로.
- Message Chains: `A->GetB()->GetC()->GetD()` 식 탐색 → 첫 객체에 메서드 하나를 두어 감춘다.
- Mysterious Name: 이름이 하는 일을 말하지 않음 → 이름을 바꾼다. 안 나오면 설계가 흐린 것이다.
- Duplicated Code: 같은 로직이 두 곳 이상 → 공통으로 빼서 둘 다 거기를 부른다.

## 4. 서브에이전트 둘을 동시에 띄운다

Agent 도구를 한 메시지에서 두 번 부른다. 서브에이전트는 이 문서도 대화도 못 본다. 필요한 것을 프롬프트에 넣는다.

규칙 축 프롬프트:
- 1절의 diff 명령과 커밋 목록
- 3절 규칙 출처 파일 경로
- 3절 냄새 12줄 전체를 그대로 붙인 것 (요약하지 않는다)
- 지시: "문서화된 규칙을 어긴 곳은 파일 · 규칙을 인용해 '위반', 냄새는 이름과 hunk 를 인용해 '판단'으로 구분.
  저장소 규칙이 기준선보다 우선. 도구가 잡는 것은 제외. 400단어 이내."

사양 축 프롬프트:
- 1절의 diff 명령과 커밋 목록
- 2절 사양 출처 (선택지 행 · 계획한 '고칠 곳' 수 · 기획서 절 · 검증 기준)
- 지시: "(a) 사양에 있는데 빠졌거나 일부만 된 것 (b) 요청하지 않은 동작(범위 이탈) (c) 구현됐지만 틀려 보이는 것.
  각각 사양 줄을 인용. 400단어 이내."
- 추가 확인:
  - '다음 요청 때 고칠 곳'이 계획과 같은 수인가. 같은 축 요청이 하나 더 온다고 치고 고칠 파일을 센다.
  - 새 플래그 · 분기 · 중복 블록이 생겼나. 있으면 A(땜질)로 흘렀다는 뜻이다.
  - 검증 기준 항목마다 대응하는 테스트나 확인이 diff 에 있나.

## 5. 모아서 보고한다

두 보고를 표 하나로 합친다. 축별로 묶고 섞어 정렬하지 않는다.

| 축 | 위치 | 내용 | 세기 |
|---|---|---|---|
| 규칙 | `WeaponComp.cpp:88` | Repeated Switches 일 수 있음 — 무기 종류 `switch` 가 3곳째 | 판단 |
| 사양 | 구조 문서 선택지 B | 다음 요청 때 고칠 곳 계획 2곳 → 구현 후 3곳 | 위반 |

- '위반': 문서화된 규칙을 어김, 또는 사양이 빠졌거나 틀림. '판단': 냄새와 취향.
- 발견이 없으면 "규칙 0 · 사양 0" 한 줄만 쓴다. 판단 행이 많으면 상위 5개만 쓰고 나머지는 건수로 적는다.
- 표 아래에 `추천: <고칠 것 하나> — <이유>` 한 줄을 붙이고 멈춘다. 고칠지는 사용자가 정한다.
- 이 리뷰는 코드를 읽은 판정이다. 동작 확인은 `game-testing` 표기로 따로 적는다.

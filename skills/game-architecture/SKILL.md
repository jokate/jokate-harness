# game-architecture — 구현 전에 구조를 조사한다

에이전트는 국소 수정에 강하고 모듈을 가로지르는 추론에 약하다. 요청 한 건을 통과시키는 패치는
돌아가지만, 같은 종류의 요청이 올 때마다 고칠 곳이 늘어난다(change amplification).
이 스킬은 그 반대 방향 — 과설계 — 도 같이 막는다. 근거는 [references/evidence.md](references/evidence.md).

## 0. 진입 판정

- diff 를 한 문장으로 설명할 수 있는 수정(오타, 값 조정, 명백한 버그)은 이 절차를 건너뛰고 바로 구현한다.
- 새 기능, 새 종류(캐릭터·무기·스킬·UI 화면…), 두 모듈 이상을 건드리는 변경이면 아래를 밟는다.
- 사용자가 "그냥 빨리"라고 하면 1줄로 트레이드오프만 말하고 따른다.
- 사용자가 직접 구조를 냈어도("이렇게 짜자") 위 둘째 줄(새 기능 · 새 종류 · 두 모듈 이상)에 들면 그대로 구현하지 않고 이 절차를 밟는다. 그 안은 3절 선택지의 한 행이 된다.
- 구현이 아니라 패턴 비교만 묻는 질문이면 [references/patterns/README.md](references/patterns/README.md) 의 '쓰는 법'대로 후보 2~3개와 얻는 것 · 잃는 것 · 쓰지 말 때, 추천 하나(이유 한 줄)를 내고 멈춘다.
- 요청 없이 "구조 개선할 곳", "리팩터링 후보"를 찾는 요청이면 [references/scan.md](references/scan.md) 로 후보를 내고, 고른 후보로 1절부터 밟는다.

## 1. 요청을 축으로 분해한다

요청을 **언제(트리거) / 무엇을(효과) / 어떤 조건으로(게이트) / 누구에게(대상)** 로 쪼갠다.
기획서가 근거면 `game-design-doc` 의 사양 표로 먼저 뽑는다 (같은 축이다). 빈칸은 '질문'으로 모은다.
프로젝트 용어집이 있으면 그 말로 쓰고, 어긋나는 말은 그 자리에서 짚는다 (game-design-doc [references/terms.md](../game-design-doc/references/terms.md)).
빈칸 때문에 조사를 더 못 하면 그 자리에서 멈추고 **질문 표**로 묻는다(아래 '질문 쓰는 법'). 답 없이도 갈 수 있으면 문서의 '질문' 절에 둔다.
그리고 같은 축의 과거 요청을 2~3건 찾는다 — 기획서, 결정 기록, `evidence.py focus`, VCS 로그 메시지.

산출: "앞으로 바뀔 설계 결정" 목록 (Parnas: 모듈은 바뀔 결정 하나를 숨기도록 나눈다).

## 2. 구조를 조사한다 (읽기 전용, 출력이 크면 서브에이전트)

1. `game-onboard` 로 엔진·모듈 맵을 잡는다. `gq.py deps --mermaid` 로 현재 모듈 그래프.
2. **기존 확장 지점**을 목록화한다. 새 구조를 만들기 전에 이미 있는 축에 얹을 수 있는지가 먼저다.
   - UE: Subsystem, Component, GAS(Ability/Effect/Cue), Game Feature Action, DataAsset/DataTable, 인터페이스, 델리게이트
   - Unity: asmdef 경계, ScriptableObject(데이터·이벤트 채널), 컴포넌트, DI 컨테이너, ECS System
   - 프로젝트 고유: 이미 있는 레지스트리·디스패처·데이터 테이블 (이게 제일 중요하다)
3. 변경 이력 신호를 뽑는다. 이 단계를 건너뛰지 않는다 — VCS 가 없을 때만 생략하고 그렇다고 적는다.
   - 먼저 소스 저장소를 확정한다: `python ~/.claude/skills/game-architecture/scripts/evidence.py roots`
     (소스가 루트와 별도 저장소인 프로젝트가 흔하다. SessionStart 의 `[game-harness]` 줄에도 나온다)
   - `python ~/.claude/skills/game-architecture/scripts/evidence.py hotspots --path <소스저장소>` — 자주 바뀌는 단위 (상대 churn 포함)
   - `python ~/.claude/skills/game-architecture/scripts/evidence.py coupling --path <소스저장소> --mermaid` — 함께 바뀌는 쌍
   - `python ~/.claude/skills/game-architecture/scripts/evidence.py focus <이번에 건드릴 파일 조각> --path <소스저장소>` — 이 파일이 바뀔 때 따라 바뀌어 온 것
   - 출력에 `⚠` 경고가 붙으면 그 안내대로 `--path` 를 바꿔 다시 돌린다.
   - 그래도 커밋이 적으면(수십 개 미만) 신호가 약하다고 밝히고 정적 구조만으로 판단한다.
4. 교차 판정:
   - co-change 높음 + 정적 의존 없음 → **숨은 결합**. 이번 변경이 그 결합을 늘리는지 본다.
   - 이번 수정 대상이 hotspot 상위 → 거기에 분기를 더 얹는 것은 **땜질 금지 구역**.
   - fan-in 높은 모듈·헤더 → 변경 위험 구역. 인터페이스를 바꾸면 파급이 크다.

신호 해석과 한계: [references/signals.md](references/signals.md)

## 3. 선택지를 2~3개 낸다

| 선택지 | 내용 |
|---|---|
| A. 국소 패치 | 기준선. 항상 포함한다 — 비교 대상이 있어야 B·C 의 비용이 보인다 |
| B. 기존 확장 지점 활용 | 2단계에서 찾은 축에 얹는다 |
| C. 새 구조 | 패턴 이름을 명시 — 후보는 [references/patterns/README.md](references/patterns/README.md) 의 증상 표에서 |

선택지는 **표 한 장, 선택지당 한 행**으로 낸다 (줄글로 풀지 않는다):
- **다음 요청 때 고칠 곳**: 개수 + 땜질 여부. 답이 "새 필드 추가", "새 분기 추가"면 땜질로 표시. 파일 이름은 근거로.
- **얻는 것 / 잃는 것**: 각 칸 한 구절.
- **근거**: 2단계 신호 중 이 선택지를 지지·반대하는 것 — 한 구절, 자세한 수치는 '근거' 절.

새 시스템 · 경계 · 데이터 구조를 정하거나 사용자가 직접 구조를 냈으면, 추천을 붙이기 전에 [references/critique.md](references/critique.md) 로 반대 검토를 한다.
누가 낸 안인지 모르는 비판자가 안마다 오류 가능성과 질문을 내고, 질문은 두 바퀴까지, 끝은 '가장 덜 나쁜 안'이다(사용자 결정 2026-11-03).

표 아래에 `추천: <선택지> — <이유 한 줄>` 을 붙인다. 이유는 표의 '다음 요청 때 고칠 곳'과 근거에서 온다. 고르는 것은 사용자다 — 추천을 붙여도 5절에서 멈춘다(사용자 결정 2026-10-27).
읽어서는 못 가르는 선택(상태 모델이 경우를 다 버티나, 느낌이 맞나)이면 버리는 프로토타입을 선택지 옆에 제안한다 — 사용자가 동의하면 만든다: [references/prototype.md](references/prototype.md).

과설계 가드: 새 추상화(C)는 **같은 축의 요청 증거가 2건 이상**일 때만 제안한다. 1건이면 "지금은 A/B, 두 번째 요청이 오면 C" 로 적는다.
- 지우기 시험: 새로 넣을 층을 지웠다고 쳐 본다. 복잡함이 호출하는 곳 여러 군데로 다시 퍼지면 값을 하는 층이다. 그냥 사라지면 전달만 하는 얇은 층이다.
- 구현체가 하나뿐인 인터페이스 · 경계는 가짜다. 실제로 갈리는 구현이 둘 이상일 때만 만든다(위 "2건 이상"과 같은 규칙).

### 질문 쓰는 법

구조를 잡다 사용자 답이 필요하면 줄글로 풀지 않고 **질문 표 하나**로 낸다 — 문서 '질문' 절과 대화창 둘 다.

| # | 질문 | 갈래 | 추천 | 답에 따라 바뀌는 것 |
|---|---|---|---|---|
| 1 | NPC 도 상호작용 조건을 갖나? | 예 / 아니오 / 모름 | 예 — 기획서 3장에 NPC 대화 조건 | 예면 슬롯 3개, 아니오면 2개 |

- 한 행에 질문 하나, 한 줄. 갈래는 2–3개로 닫고 '모름' 을 둘 수 있다.
- 추천 칸에 갈래 하나와 이유 한 구절. "예" 라고만 답하면 추천을 받아들인 것이 되게 묻는다.
- '답에 따라 바뀌는 것' 에 선택지 · 구조 · 작업량 중 무엇이 바뀌는지 적는다. 안 바뀌면 묻지 않는다.
- 막는 질문(답 없이는 조사를 못 이어 감)을 위에, 나중에 정해도 되는 질문을 아래에. 5개 이하.
- 사실은 직접 찾는다. 코드 · 인덱스 · 기획서 · 위키로 알 수 있는 것은 묻지 않는다. 사용자에게는 결정만 묻는다.
- 지금 답할 수 있는 질문만 낸다. 이번 표의 다른 질문 답에 달린 질문은 그 답을 받은 뒤 다음 표로 낸다.

답 읽기 (AI-DLC 에서 빌림, `docs/UPSTREAM.md`):
- 번호 · "좋아" · 오타도 고른 것이다. 갈래를 정말 모를 때만 한 번 짧게 되묻는다.
- "B 로 하되 이름은 X 로"처럼 고름과 지시가 한 문장이면, 고른 것으로 치고 지시를 하고, 바꾼 것을 한 줄로 알린다. 다시 묻지 않는다.
- 답 없이 질문만 왔으면 답하고 멈춘다. 다음 말이 고른다.
- 반박이 오면 새 근거(사실 · 제약 · 기획)가 있을 때만 판단을 바꾸고 무엇 때문인지 적는다. 근거 없이 같은 말이면 판단을 유지하고 그렇다고 말한다.
- 고른 것은 반박이 아니다. "그래도 B"면 B 로 간다. 내 반대는 '남은 반대'에 한 줄로 남기고 다시 묻지 않는다.
- 같은 안을 세 번째 고쳐 달라고 하면 갈래에 '지금 것으로 진행'을 더한다.
- 이미 만든 구조 문서가 있는 주제로 다시 오면 '그대로 / 고치기 / 새로' 셋 중 추천을 붙여 묻는다.

## 4. 근거를 그림으로 낸다

**구조도는 반드시 그린다 — Before/After 를 diagram-design 으로.** 사용자 요청(2026-10-20).
**형식은 "무엇이 바뀌나" 로 고른다 — 구조 질문이라고 아키텍처 그림이 아니다.** 연결이 바뀌면 Architecture delta,
상태 · 전이면 State machine, 호출 순서면 Sequence, 판정 분기면 Flowchart, 데이터 구조면 ER, 상속 → 조합이면 UML class …
표와 규칙: [references/diagram-types.md](references/diagram-types.md). 사용자가 형식을 말하면 그것을 쓴다.
- 그림 절 첫 줄에 `바뀌는 것: <한 줄> → <형식>`. 형식은 한 문서에 두 가지까지.
- 선택지마다 전 · 후: Architecture delta 는 한 장, 그 밖의 형식은 같은 배치의 두 장(바뀐 요소만 강조). 독자 `engineer`, 형식별 예산은 diagram-design 의 type 문서대로.
- 파일은 문서와 같은 폴더에 `<문서 이름>-구조-<선택지>-<형식>[-전|-후].html` (예: `20261020-조건-구조-C-sequence-전.html`). render.py 가 '그림' 절에 이름순으로 끼워 넣는다.
- diagram-design 이 없으면(`~/.claude/skills/diagram-design`) `setup.bat` 을 다시 돌리라고 알리고 아래 Mermaid Before/After 로 대신한다.
- 기록 `.md` 의 Mermaid 는 그대로 둔다(원본, diff 된다). 구조도가 있으면 HTML 에서는 접힌 'Mermaid 원본'으로 내려간다.

Mermaid 규칙 (렌더러 호환 — 어기면 GitLab·Azure DevOps·SVN HTML 에서 깨진다):
- Mermaid 는 `graph TD` / `graph LR` 와 `sequenceDiagram` 만. `flowchart` 키워드, C4 문법 금지. subgraph 제목은 `subgraph id["제목"]`.
- 노드 15개 이하, 그림 하나에 주장 하나. 수치는 간선 라벨에.
- Before/After 는 선택지별 subgraph 로 나누고, 제목에 "다음 요청 때 N곳"을 적는다.

템플릿: [references/diagrams.md](references/diagrams.md). 최소 세트:

1. **현재 구조도** — 관련 모듈·클래스만, 노드 15개 이하
2. **Before/After change-impact** — "다음 같은 요청"이 왔을 때 선택지별로 고치는 노드를 강조. 노드 수가 곧 change amplification 수치
3. **신호 표** — hotspot·co-change 상위 (evidence.py 출력 그대로)
4. 이벤트·델리게이트·SO 채널 흐름이 핵심이면 sequence 다이어그램 1장 추가

**그림은 반드시 렌더해서 보여 준다.** Claude Code 대화창은 Mermaid 를 그리지 않고 코드로만 보인다 — 코드 블록만 내면 사용자는 그림을 못 본다.
1. 답변 전체(아래 출력 형식 그대로, mermaid 블록 포함)를 `<프로젝트>/Saved/ClaudeArch/<YYYYMMDD>-<주제>.md` 로 저장한다 (Unity 는 `Library/ClaudeArch/`. 프로젝트 인덱스와 같은, VCS 가 무시하는 폴더다).
2. 위 그림(diagram-design, 바뀌는 것에 맞는 형식)을 `<문서 이름>-구조-<선택지>-<형식>[-전|-후].html` 로 저장한다.
3. `python ~/.claude/skills/game-architecture/scripts/render.py <그 파일.md> --open` — 단일 HTML 을 만들고 브라우저로 연다. mermaid·marked 는 `scripts/vendor/` 에 동봉돼 있어 설치·인터넷이 필요 없다.
   HTML 은 **한눈에 · 선택지 · 그림(구조도) · 질문을 맨 위**에 두고 나머지는 접힌 '근거'로 내린다. 보이는 부분의 120자 넘는 줄은 첫 문장만 남기고 접는다(전부 펼치려면 `--full`).
   출력 끝의 `읽기 점검:` 줄이 기준(첫 화면 30줄 · 긴 줄 0 · 첫 화면 몰아 쓴 줄 0 · 날짜 꼬리표 0 · 첫 화면 번호 0 · 근거 밖 절 0 · 구조도 1장 이상 · 추천의 왜 네 칸 · 근거 육하원칙 표)을 넘으면 아래 '읽기 규칙'대로 고쳐 다시 저장 · 렌더한다.
4. 대화창에는 mermaid 코드를 다시 붙이지 않는다. 한눈에 2줄 · 선택지 한 줄씩 · 질문 표 · HTML 경로만 적는다.

렌더는 위 3번이 한다 — 대신 돌아 주는 훅은 없다(Stop 훅 diagram_view 는 15일 0회 동작해 2026-10-22 에 뺐다). 저장했으면 `render.py --open` 까지 직접 돌린다.
파일 쓰기가 막혀 있으면(읽기 전용 세션) mermaid 블록을 대화에 내고, 그림으로 보려면 저장 후 render.py 를 돌리라고 한 줄 적는다.
사용자가 다른 위치를 정하면 거기에 저장한다.

## 읽기 규칙 — 문서는 줄글이 아니라 판단 재료다

사용자는 설계 판단만 읽는다. 렌더된 HTML 은 '근거' 위(첫 화면)만 읽어도 판단할 수 있어야 한다.
규칙의 근거와 출처는 하네스 `docs/READING.md`.

1. **첫 화면 글 30줄 이하**(그림은 한 장에 한 줄로 센다) — 한눈에 · 선택지 표 · 구조도 · 질문 표만. 나머지는 '근거' 절(HTML 에서 접힌다).
2. **한 줄에 사실 하나, 120자 이하.** "~고, ~며, ~해서" 로 잇지 않고 줄을 나눈다. 괄호와 가운뎃점으로 사실을 이어 붙이지 않는다 — 가운뎃점 3개나 괄호 2개가 한 줄에 있으면 몰아 쓴 줄이다.
   줄 · 소제목 · 표 첫 칸은 첫 두 낱말에 핵심을 둔다. 소제목은 결론 문장으로 쓴다("피해는 한 곳에서 받는다"). 꾸밈말 없이 사실만.
3. **줄글 문단 금지.** 셋 이상 나열은 목록, 둘 이상 비교는 표.
4. **파일:줄 · 커밋 번호 · 작업 번호 · 세부 수치는 '근거' 절 표에만.** 첫 화면에는 판단에 쓰는 숫자만("4곳", "853개").
5. **본문은 단정한다. 확신은 표의 열**(확인 / 추정 / 모름)로 적는다. 문장마다 "~로 보인다" 를 섞지 않는다.
6. **문서는 '근거' 절에서 끝난다.** 설계 노트 · 검증 기준 · 범위 밖 · 부록 같은 절을 붙이지 않는다. 구현 설계와 검증 기준은 사용자가 고른 뒤 5단계 계획에서 다룬다.
7. **지금 상태만 쓴다.** 날짜 · 시각 꼬리표("[18시 갱신]", "16:34 뒤")를 문서 어디에도 쓰지 않는다. 바뀌면 그 자리를 고쳐 쓴다.
8. **지어낸 이름은 처음 나올 때 한 구절로 푼다.** 사용자가 쓰지 않은 말이면 풀이 없이 쓰지 않는다.
9. **근거는 육하원칙 표**(누가 · 언제 · 어디서 · 무엇을 · 어떻게 · 왜 · 확신)로 — 출력 형식의 '확인한 사실'.
10. **추천 밑에 왜 네 칸**(문제 · 버린 안 · 대가 · 뒤집는 조건)을 자세히 쓴다. 한 줄에 사실 하나. 양식은 `docs/READING.md` '결정 블록'.
11. `render.py` 가 찍는 **읽기 점검**이 기준을 넘으면 줄이거나 표로 바꿔 다시 저장하고 다시 렌더한다.

## 5. 멈춘다

선택지와 그림을 내고 **멈춘다.** 고르는 것은 사용자다. 선택되면:
1. 인터페이스 모양이 열려 있고 두 모듈 이상을 건드리면 [references/interface-design.md](references/interface-design.md) 로 3안을 비교하고 추천한 뒤 다시 멈춘다. 아니면 건너뛴다.
2. 선택된 구조로 계획을 세운다 — 검증 기준(빌드·테스트·PIE 확인 항목)을 구현보다 먼저 적는다 (`game-testing`).
   계획이 고른 선택지와 어긋나면(고칠 파일 · 경계 · 새 모듈이 선택지 행과 다르다) 차이를 한 줄씩 보여 주고 멈춘다. 같으면 바로 3으로 간다(사용자 결정 2026-11-03).
3. 구현한다. 빌드 · 테스트가 실패하면 `game-testing` 의 실패 사다리로 간다.
4. 구현 후 [references/review.md](references/review.md) 대로 리뷰를 맡긴다: 규칙 축 · 사양 축 서브에이전트 둘을 동시에.
   사양 축이 보는 것: 새 플래그·분기·중복 블록, 범위 이탈, "다음 요청 시 고칠 곳 수"가 계획과 같은가.
   판정이 '다시'면 위반만 고치고 다시 리뷰한다(2회까지). 판단 행 · 구조를 바꾸는 고침은 사용자에게 넘긴다.
5. 위키 하네스(jokate-wiki)를 쓰는 프로젝트면 고른 구조를 위키에 남긴다: `wiki-ingest` 로 그 시스템 쪽을 고친 뒤
   `python ~/.claude/wiki-harness/scripts/wq.py confirm --wiki <위키 폴더> systems/<파트>/<시스템>.md` 로 확정한다
   (사용자가 직접 구현한 구조만 확정한다 — 확인 질문 3–5개는 wiki-ingest 가 낸다). 위키가 없으면 이 단계는 건너뛴다.
   결정 이유를 따로 남기는 것은 세 조건이 다 맞을 때만이다: 되돌리기 어렵다 · 맥락 없이 보면 놀랍다 · 진짜 트레이드오프였다 (terms.md).
   반대 검토를 했으면 풀리지 않은 '남은 반대'도 같이 남긴다 (critique.md 8절).

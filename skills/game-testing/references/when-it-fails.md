# 실패했을 때 — 고치는 사다리

> 일부를 AWS AI-DLC(`aidlc-workflows` 의 build-and-test · loopback · checkpoint 프로토콜, MIT-0)에서 빌려 게임 프로젝트에 맞게 고쳤다.
> 라이선스: `docs/third_party/aidlc-workflows-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

빌드 · 테스트 · 정해 둔 확인 항목이 하나라도 실패하면 이 순서를 밟는다. 같은 실패를 세 번째 고치려 하면 이미 4단이다 (stuck_watch 경고와 같은 신호).

## 0. 바닥 규칙

- 기준을 낮추거나 끄는 것은 수정이 아니다. 허용 오차 넓히기, 시간 제한 늘리기, 테스트 건너뛰기 · 지우기, 검사 끄기가 그렇다.
- 검증 명령은 계획 때 하나로 정해 적는다. 끝날 때 그 명령을 그대로 돌린다. 몰래 더 좁은 명령으로 바꾸지 않는다.
- 못 돌린 검사는 통과가 아니다. `검증 안 됨 — 못 돌림: <이유>` 로 쓴다. "나중에 CI 가 돌린다"도 못 돌린 것이다.
- 파일이 생겼다, 컴파일됐다, 응답이 성공이다 — 모두 검증이 아니다.

## 1. 제자리에서 고친다 — 2회까지

원인이 테스트 설정 · 빌드 스크립트 · 환경(에디터 잠금, DDC, 경로)에 있을 때만.
실패 출력을 읽고, 고치고, 실패한 단계만 다시 돌린다.

## 2. 원인을 가르고 영향을 잰다

1단을 다 썼거나 원인이 구현 쪽이면:
- 원인이 어디인가: 구현 코드 · 테스트 코드 · 고른 접근(엔진 기능, 플러그인 · 버전, 알고리즘, 설정값).
- 바꿀 수 있는 곳의 수정안을 찾고 영향을 적는다: 작업량 · 위험 · 다른 시스템에 닿는 곳.
- 영향을 재지 않고 "범위 밖"이라고 하지 않는다.

## 3. 구현으로 돌아간다 — 3회까지

수정안이 있고 고른 구조 안에서 고칠 수 있으면 구현으로 돌아가 고친다.
돌아갈 때마다 테스트 문서(`references/test-doc.md` 로 만든 것)의 `## 되돌아간 기록` 에 한 항목을 쌓는다. 지우지 않는다.

```
### 되돌아감 N — <날짜 시각>
- 진단: <무엇이 왜 실패했나>
- 원인: <구현 | 테스트 | 고른 접근> — <파일 · 결정>
- 고친 것: <한 줄>
- 영향: <작업량 · 위험>
```

- 진단이 가리킨 곳만 다시 연다. 나머지 작업은 그대로 둔다.
- 고침이 고른 선택지를 벗어나면(경계 · 모듈이 바뀜) 돌아가지 말고 4단으로 간다.

## 4. 멈추고 묻는다

3회를 다 썼거나, 수정안이 없거나, 구조를 바꿔야 하면 멈춘다. 포기는 사용자가 정한다.

```
빌드 · 테스트 실패: <오류 한 줄>
원인: <진단> · 수정안: <수정> — 영향 <작업량 · 위험> · 되돌아감 N/3
```

| # | 질문 | 갈래 | 추천 | 답에 따라 바뀌는 것 |
|---|---|---|---|---|
| 1 | 어떻게 할까? | 고쳐서 다시 / 실패로 두고 진행 / 중단 | <갈래> — <한 구절> | 다음 작업 |

- 수정안이 없으면 '고쳐서 다시'를 빼고 두 갈래만 낸다. 수정안을 지어내지 않는다.
- '실패로 두고 진행'이면 검증 상태는 `검증 안 됨 — 실패 남김: <테스트 이름>` 이다.

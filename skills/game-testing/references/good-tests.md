## 좋은 테스트

- 바깥에서 보이는 동작을 확인한다. 공개 함수의 반환값, 어빌리티 발동 결과, 이벤트·델리게이트로 확인한다.
- 이름이 사양처럼 읽힌다. 예: `Game.Damage.Grade2_NoStagger_DrainsGroggy` (등급 2 적은 경직 없이 그로기 게이지가 깎인다).
- 내부 구조를 바꿔도 동작이 같으면 깨지지 않는다.
- 테스트 하나에 확인하는 동작은 하나다.

## 나쁜 모양

| 모양 | 알아보는 법 | 대신 |
|---|---|---|
| 구현에 묶임 | private 멤버나 내부 함수를 직접 본다. 같은 모듈의 협력 객체를 목(mock)으로 바꾼다. 호출 횟수·순서를 센다. 리팩터링만 했는데 깨진다 | 공개 함수, 발동 결과, 이벤트로 확인한다 |
| 동어반복 | 기대값을 코드와 같은 공식으로 다시 계산한다(`Expected = Base * Mult`). 공식이 틀려도 통과한다 | 기획서 예시 숫자를 쓴다. 손으로 계산한 리터럴을 쓴다 |
| 가로 자르기 | 테스트를 한꺼번에 먼저 다 쓰고 나서 구현한다. 상상한 모양만 시험하게 된다 | 실패하는 테스트 하나 → 통과할 만큼만 구현 → 다음 |
| 옆길로 확인 | 동작 대신 저장 상태(세이브 파일, DataTable 행, 액터 내부 값)를 들여다본다 | 같은 공개 경로로 다시 읽어 확인한다 |

## 목(mock)은 바깥 경계에만

- 쓰는 곳은 정해져 있다: 네트워크, 플랫폼 SDK(업적·결제), 파일, 시간, 랜덤.
- 같은 모듈의 클래스나 직접 만든 컴포넌트는 실제 것을 쓴다.
- 시간과 랜덤은 목 대신 고정한다. 시드를 고정하고, 틱 델타를 고정한다(UE `FApp::SetUseFixedTimeStep` · `SetFixedDeltaTime`, Unity `Time.captureDeltaTime`).
- 테스트 하나 때문에 인터페이스를 새로 만들지 않는다. 구현체가 실제 하나뿐이면 그 경계는 아직 가짜다.
  시험용 구현체까지 둘이 필요할 때만 만든다.

## 테스트 위치(경계) 고르기

- 경계는 호출하는 쪽과 테스트가 같이 지나가는 공개 면이다. 테스트는 거기에 둔다. 내부를 직접 찌르지 않는다.
- 위치마다 "잡는 것 · 놓치는 것"을 한 구절씩 적는다. 예: "피해 공식 함수 — 수치를 잡고, 발동 조건은 놓친다".
- 모든 경우를 다 시험할 수는 없다. 자주 바뀌는 곳과 복잡한 판정에 몰아서 둔다.

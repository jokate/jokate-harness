# game-testing — 검증 기준을 구현보다 먼저

게임 코드는 상당 부분이 에디터·런타임에서만 확인된다. 그래서 검증 상태를 세 단계로 구분해 쓴다.

| 표기 | 의미 |
|---|---|
| **검증됨(자동)** | 자동 테스트가 돌았고 통과. 명령과 결과를 같이 적는다 |
| **검증됨(수동)** | 사람이 PIE·플레이모드에서 확인. 누가, 무엇을 봤는지 |
| **검증 안 됨** | 컴파일만 됐거나 아무것도 안 돌렸다. 이 경우 반드시 이렇게 쓴다 |

"컴파일 성공"은 검증이 아니다.

## 절차

1. **계획 단계에서 검증 기준부터** — 구현 전에 "끝났다는 것은 무엇으로 아나"를 적는다. 템플릿: [references/test-doc.md](references/test-doc.md)
2. **자동화 가능 여부를 가른다**
   - 순수 로직(수치 계산, 상태 전이, 데이터 검증): 단위 테스트 → 반드시 자동화
   - 월드가 필요한 로직(스폰, 충돌, 어빌리티 발동): 기능 테스트 → 가능하면 자동화
   - 감각적 판단(타격감, 연출 타이밍, 가독성): 수동 체크리스트 → 사람 몫. 대신 확인 항목을 구체적으로
3. **테스트를 쓴다** — 엔진별 형식: [references/ue.md](references/ue.md) · [references/unity.md](references/unity.md)
4. **헤드리스로 돌린다** — 명령과 종료 코드, 실패 테스트 이름을 결과에 붙인다.
5. **결과를 적는다** — 위 표기 셋 중 하나로. 부분만 됐으면 항목별로.

## 규칙

- 테스트를 통과시키려고 테스트를 고치지 않는다. 테스트가 틀렸다고 판단되면 그 판단을 먼저 보고한다.
- 에디터가 떠 있는 상태에서 커맨드라인 테스트를 돌리면 충돌할 수 있다(에셋 잠금, DDC). 돌리기 전에 사용자에게 확인.
- MCP 로 에디터를 조작해 확인한 것은 "검증됨(수동-에이전트)"로 쓰고, 무엇을 조회해 확인했는지 적는다.
- 재현 절차가 없는 버그 수정은 수정 전 실패를 먼저 재현한다 (실패 테스트 → 수정 → 통과).

# 용어 — 프로젝트 말로 쓰고, 어긋나면 바로 짚는다

> 일부를 Matt Pocock 의 skills(`domain-modeling`, MIT, Copyright (c) 2026 Matt Pocock)에서 빌려 게임 프로젝트에 맞게 고쳤다.
> 라이선스: `docs/third_party/mattpocock-skills-LICENSE` · 원본 추적: `docs/UPSTREAM.md`.

기획서를 읽거나 사양 · 이름 · 테스트를 쓰기 전에 밟는다. 말의 뜻은 프로젝트 주인이 정한다. 우리는 맞춰 쓰고, 어긋나면 묻는다.

## 1. 용어집부터 찾는다
- 찾을 곳: 루트 `GLOSSARY.md` · `Docs/GLOSSARY.md` · 기획 폴더 · 프로젝트 위키의 용어 쪽 · CLAUDE.md 의 안내 줄
- 하나라도 있으면 그것을 쓴다. 두 번째 용어집을 만들지 않는다.
- 둘 이상 나오면 합치지 말고 어느 쪽이 기준인지 묻는다.
- 없으면 만들기 전에 묻는다. 제안 위치는 기획서 옆이나 `Docs/GLOSSARY.md`.

## 2. 쓰기 전에 읽는다
- 사양 표 · 테스트 이름 · 코드 이름 · 답변에 용어집의 말을 그대로 쓴다.
- '아닌 것' 칸에 적힌 말은 그 뜻으로 쓰지 않는다.
- 용어집에 없는 기획 용어는 추측해 쓰지 않는다. `[확인 필요]` 로 표시하고 묻는다.

## 3. 어긋나면 바로 짚는다
- 대상: 사용자 말 ↔ 용어집 · 기획서 ↔ 용어집 · 기획서 ↔ 기획서
- 모아 두지 않고 그 자리에서 한 줄로 묻는다.
  "용어집은 '경직'을 X 로 두는데 여기서는 Y 로 쓰는 것 같다 — 어느 쪽?"
- 한 말이 둘 이상을 가리키면 정밀한 이름을 제안한다.
  "'경직'이 피격 경직과 행동 불능을 다 가리킨다 — '피격 경직' · '기절' 로 가를까?"
- 사용자가 말한 동작이 코드와 다르면 같은 식으로 짚는다. 어느 쪽이 맞는지는 사용자가 정한다.
- 답을 받기 전에는 어느 쪽 뜻으로도 조용히 구현하지 않는다.

## 4. 정의는 사람이 정한다
- 에이전트는 제안하고, 기획자(프로젝트 주인)가 정한다.
- 모르는 부분과 코드 이름 대응은 주인이 확인할 때까지 `[확인 필요]`.
- 용어집 머리말에 쓰기 규칙이 있으면 그대로 따른다. 예: "에이전트는 정의를 쓰지 않는다" → 제안은 답변에만 쓴다.
- 규칙이 없으면 주인이 답한 뒤 그 줄만 더한다.

## 5. 용어집 항목 모양

| 용어 | 뜻 | 아닌 것 | 코드 이름 |
|---|---|---|---|
| 경직 (가상의 예) | 피격으로 일정 시간 행동하지 못하는 상태 | 기절 · 넉백 | `State.Hitstun` [확인 필요] |

- 뜻은 한두 문장, '무엇인가'만. 수치 · 처리 순서 · 구현 방식은 사양 표와 코드 몫이다.
- 같은 개념의 다른 말은 하나만 고르고 나머지는 '아닌 것' 에 둔다.
- 이 프로젝트에만 있는 말만 넣는다. 일반 게임 · 프로그래밍 용어는 뺀다.
- 코드 이름은 GameplayTag · 클래스 · DataTable 행 이름. 없으면 비우고, 모르면 `[확인 필요]`.
- 이미 모양이 있는 용어집은 그 모양을 따른다.

## 6. 결정 기록은 아껴서
- 셋이 모두 맞을 때만 쓴다: 되돌리기 어렵다 · 맥락 없이 보면 놀랍다 · 진짜 트레이드오프가 있었다.
- 하나라도 빠지면 쓰지 않는다. 용어 하나의 뜻은 용어집 한 줄로 끝낸다.
- 위키 하네스를 쓰면 위키에 남긴다: `game-architecture` §5 5단계(`wiki-ingest` → `wq.py confirm`).
- 아니면 기획서나 `Docs/` 옆에 결정 노트 하나, 10줄 안쪽.

```
제목:
상황:
결정:
버린 안과 이유:
결과:
```

## 7. 시나리오로 다듬기
- 용어가 만나는 경계를 구체적인 상황 하나로 시험한다. 예: "슈퍼아머 중 경직기를 맞으면?"
- 한 번에 하나씩, 답할 수 있는 주인에게 묻는다. 코드나 기획서에서 찾을 수 있으면 묻지 않고 찾는다.
- 답이 나오면 주인 확인 후 해당 항목의 '뜻' · '아닌 것' 에 반영한다. 수치 · 처리 규칙이면 사양 표로 보낸다.

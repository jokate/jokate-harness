# game-design-doc — 기획서를 사양으로, 사양을 구현에 대응시킨다

기획서는 사람이 읽으라고 쓴 글이라 조건·예외·수치가 문장 속에 흩어져 있고, 빠진 것은 안 보인다.
구현자가 빈칸을 추측으로 메우면 그게 나중에 "기획과 다르다"가 된다. 이 스킬은 빈칸을 **보이게** 만든다.

## 규칙

1. 기획서는 통째로 읽지 않는다. `python ~/.claude/skills/game-onboard/scripts/gq.py get <문서>` 로 목차 → 필요한 절만.
   사내 기획서가 Confluence·엑셀·PPT 면 사용자에게 내보내기(md/csv/pdf)를 받아 같은 방식으로 본다.
2. 기획서를 고치지 않는다. 구현과 어긋나면 **어긋난다고만** 알린다. 어느 쪽을 고칠지는 사용자가 정한다.
3. 기획에 없는 것을 추측으로 채우지 않는다. "판단 대기"로 모아 사용자(기획자)에게 묻는다.
4. 인용은 `문서#절` 좌표로. 사양 한 줄마다 출처가 있어야 한다.

## 절차

### 1. 사양 표로 뽑는다

기획 문장을 아래 축으로 쪼갠다. `game-architecture` 의 요청 축과 같은 축이다 — 사양이 곧 구조 판단의 입력이 된다.

| ID | 언제(트리거) | 무엇을(효과) | 조건(게이트) | 대상 | 수치 | 예외·금지 | 출처 |
|---|---|---|---|---|---|---|---|

- 한 칸이라도 기획에 없으면 `?` 로 두고 판단 대기에 올린다. 흔한 빈칸: 중첩 규칙, 취소·중단 시 처리, 동시 발동 우선순위, 네트워크(누가 판정하나), 수치의 단위.
- 수치는 단위까지. "빠르게", "잠깐" 같은 말은 수치가 아니다 → 판단 대기.

템플릿과 예시: [references/spec-table.md](references/spec-table.md)

### 2. 구현과 대응시킨다

사양 ID 마다 구현 좌표와 상태를 붙인다. 좌표는 `gq.py find/sym` 과 소스 `file:line`, 애셋 경로.

| 상태 | 의미 |
|---|---|
| 구현됨 | 코드·데이터가 사양대로. 근거 좌표 필수 |
| 부분 | 일부 조건·예외가 빠짐. 무엇이 빠졌는지 |
| 없음 | 구현 흔적 없음 |
| 어긋남 | 구현이 사양과 다르게 동작. 양쪽 좌표를 나란히 |
| 확인 불가 | BP·애셋 안에 있어 소스로 못 봄 → MCP 조회(`game-mcp`) 또는 사용자 확인 |

구현 상태 문서(진행 기록·체크리스트)가 따로 있으면 그것도 대조한다. 문서끼리 어긋나는 것도 보고 대상이다.

### 3. 수치가 어디 사는지 본다

기획 수치가 **데이터**(DataTable / DataAsset / ScriptableObject / 커브)에 있는지 **코드 상수**인지 구분한다.
코드 상수면 "기획자가 조정할 수 없다"를 한 줄로 알린다 — 옮길지는 구조 판단(`game-architecture`)이다.

### 4. 보고한다

```
## 사양 (<문서#절>)
(사양 표)

## 구현 대응
(ID · 상태 · 좌표)

## 판단 대기 (기획)
1. <빈칸> — 왜 필요한가 한 줄

## 어긋남
- <사양 ID>: 기획 <문서#절> ↔ 구현 <file:line> — 차이 한 줄
```

### 5. 다음 층으로 넘긴다

- 구현하려면 → `game-architecture` (사양 표를 요청 축으로 그대로 쓴다)
- 완료 기준이 필요하면 → `game-testing` (사양 ID 하나당 완료 기준 한 줄 이상)

# CLAUDE.md 템플릿

원칙 (공식 권고): 200줄 미만 · 규칙에는 이유를 붙인다 · "이 줄을 지우면 Claude 가 실수하나?"가 아니면 뺀다 ·
코드를 읽으면 알 수 있는 것, 자주 바뀌는 것은 넣지 않는다 · 강조(IMPORTANT/CRITICAL)는 쓰지 않는다 — 최신 모델은 과잉 반응한다 ·
절차는 스킬로, 반드시 지켜야 하는 금지는 훅으로.

[필수] 모듈은 항상 넣고, [선택] 모듈은 인터뷰에서 고른 것만 넣는다. `<…>` 는 채운다.

---

```markdown
# CLAUDE.md — <프로젝트> 작업 규칙

## 전제 [필수]
- 판단권자는 <사람/팀>다. Claude 는 구현 보조다. 기획("무엇을, 왜")은 대신 정하지 않는다.
- 이유: 설명할 수 없는 코드가 쌓이면 유지보수가 불가능해진다.

## 기술 컨텍스트 [필수]
- 엔진: <UE 5.x / Unity 6000.x>. 버전에 따라 다른 API 는 버전을 먼저 밝힌다.
- VCS: <git / svn>. 커밋·푸시는 요청받을 때만.
- 빌드·실행: <명령 또는 "에디터에서"> · 테스트: <명령>

## 조회 [필수]
- 요청을 받으면 파일 탐색보다 먼저 맞는 스킬을 부른다: 구조·위치·엔진 API → game-onboard · 기획서 → game-design-doc · 테스트 → game-testing · 에디터 MCP → game-mcp.
- 문서·소스를 통째로 읽지 않는다. `python ~/.claude/skills/game-onboard/scripts/gq.py map | find | sym | get` 으로 좌표부터.
- 인덱스는 세션 시작 훅이 갱신한다. `[낡음]` 이 뜨면 `index`.
- 이유: 이 파일이 없는 프로젝트에서는 스킬이 불리지 않고 파일을 직접 훑었다 (2026-10-01 평가). 훅 안내로는 대체되지 않았다.

## 범위 [필수]
- 요청하지 않은 리팩터링·파일 생성·기능 추가를 하지 않는다. 다음 단계가 보이면 한 줄 제안 후 멈춘다.
- 선택지가 여럿이면 나열하고 멈춘다.

## 정직 [필수]
- 확인 못 한 API·시그니처는 "확인 필요"로 쓴다. 돌려보지 않은 것은 "검증 안 됨"으로 쓴다.
- 이유: 틀린 답은 답이 없는 것보다 비싸다.

## 구조 [선택: 권장]
- 기능 요청은 구현 전에 game-architecture 절차를 밟는다. 케이스마다 필드·플래그·분기를 덧붙이지 않는다.
- 제안에는 "같은 종류의 요청이 또 오면 어디를 고치나"를 한 줄로 붙인다.

## 답변 형식 [선택]
- 결론 먼저, 근거 한두 줄. 원인을 물으면 원인만, 구현을 물으면 전체 코드.
- 설계 판단은 "A 는 X 를 얻고 Y 를 잃는다" 한 줄. 추천하지 않는다.

## 가설 우선 [선택: 개인 학습용]
- 질문에 `## 내 가설` 이 있으면 맞는지부터 판정하고, 틀리면 어디서 어긋났는지 짚는다.
- 가설이 없으면 "먼저 가설 한 줄만"이라고 되묻는다. `[SKIP]` 이면 바로 답한다.

## 막혔을 때 [선택]
- `[MUCK]` 이면 답 대신: 풀려는 문제를 한 문장으로 되묻고, 이미 시도한 것을 나열하게 한다.

## 기획 문서 [선택]
- `<경로>` 는 참고용이다. 구현과 어긋나면 어긋난다고만 알린다. "기획서 업데이트"라고 할 때만 고친다.

## 주석 [선택]
- 주석은 이유가 코드에 드러나지 않을 때만.
```

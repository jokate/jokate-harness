# diff-proto — 구현을 확인받아 확정한다

이름은 프로토지만 버리는 시안이 아니다. 여기서 확인받은 코드가 그대로 적용된다(사용자 결정 2026-11-19).
사용자는 모든 코드를 보지 않는다. 핵심 설계 포인트와 핵심 구현 포인트를 확인한다(사용자 결정 2026-11-26).
기능 구현만이 아니다. 버그를 고친 것도 같은 순서로 확인받는다.
느낌 · 규칙을 먼저 돌려 보는 버리는 프로토타입은 `game-architecture` 의 `references/prototype.md` 다.

## 순서

1. 볼 변경을 정한다.
   - 인자가 '무엇을 짜라' 면 본 구현을 작업 사본에 쓴다. 고른 구조와 계획대로 쓴다. 커밋하지 않는다.
   - '이미 바뀐 것을 보여 달라' 면 쓰지 않는다. 지금 작업 사본의 변경을 그대로 본다.
   - 앞서 확인받던 중이면 남은 hunk 부터 본다: `python ~/.claude/skills/selection/scripts/diffdoc.py --status --path <저장소> --project <프로젝트 루트>`
2. diff 를 읽는다. git 은 `git diff HEAD` 와 새 파일, svn 은 `svn diff`.
   파일마다 hunk(`@@` 한 덩어리)를 위에서부터 1번으로 센다.
3. 이야기 JSON 을 쓴다. 형식은 [references/story-sample.json](references/story-sample.json) 그대로다.
   - 위치: `<프로젝트>/Saved/ClaudeArch/decide/<YYYYMMDD>-<주제>-diff.json` (Unity 는 `Library/ClaudeArch/decide/`, 그 밖은 세션 임시 폴더 — `.claude/` 아래에 쓰면 권한을 묻는다).
   - 그룹은 핵심만 담는다. 설계가 드러나는 hunk 와 동작이 갈리는 hunk 다. 동작이 바뀌는 hunk 는 빠짐없이 담는다.
   - 이름 · 포맷 · 따라 바뀐 선언 · 기계적인 변경은 담지 않는다. '나머지 변경' 으로 접혀 나오고 사용자가 판정하지 않는다.
   - 그룹은 뜻이 같은 변경이다. 파일 통째보다 함수 단위 hunk 로 고른다(`경로#2`). 읽는 순서로 놓는다.
   - 새 파일은 hunk 하나가 파일 전체다. 핵심 함수만 줄 범위로 고른다(`경로:40-95`, 새 파일 쪽 줄 번호). 남은 줄은 '나머지 변경' 에 접혀 나온다.
   - `title` 은 결론 문장이다("만료된 입력은 건너뛴다").
   - `why` 는 무엇이 문제였나 한 줄. `look` 은 사용자가 눈으로 확인할 것 한 줄.
   - `risk` 는 높음 · 중간 · 낮음. 높음은 동작이 바뀌는 곳, 낮음은 이름 · 포맷 · 따라 바뀐 선언.
   - `match` 는 그 그룹의 hunk 다: `"경로"`(파일 전부) · `"경로#2"`(둘째 hunk) · `"경로#1-3"` · `"경로:40-95"`(새 파일 쪽 40~95째 줄) · `"Source/*.h"`.
   - 그룹은 7개 이하.
   - 설계 포인트 문서를 이야기 옆에 md 로 쓴다(`<주제>-설계.md`). 클래스 관계 · 책임 · 흐름이다. 표 하나나 그림 한 장(mermaid), 20줄 안팎.
4. 점검한다.
   `python ~/.claude/skills/selection/scripts/diffdoc.py <이야기.json> --doc <설계.md> --path <저장소> --project <프로젝트 루트> --check`
   - `이야기 오류` 는 diff 에 없는 것을 가리켰다는 뜻이다. 이야기를 고친다.
   - `나머지:` 줄이 접혀 나올 hunk 다. 그 안에 동작이 바뀌는 hunk 가 있으면 그룹에 넣는다.
   - `점검: 그룹 … 줄이다` 는 그룹이 120줄을 넘는다는 뜻이다. 핵심 함수만 줄 범위로 좁힌다.
   - `앞서 확인한 것` 은 앞 차례에 확인받고 그 뒤로 바뀌지 않은 hunk 다. 이야기에 담지 않는다. 페이지에 접혀 나오고 다시 묻지 않는다.
   - svn 에 올리지 않은 새 파일은 `--add <파일>` 로 준다. 작업 사본을 건드리지 않은 시안은 `--patch <파일.diff>` 로 준다.
5. 띄운다. **백그라운드로 돌린다.** `--check` 만 빼고 같은 명령이다.
   - 페이지 맨 위는 설계 포인트 문서다. 그 아래가 핵심 그룹이다.
   - 사용자는 그룹마다 '확인함' 이나 '기각' 을 누른다. 기각은 피드백이 있어야 보내진다. 한 번에 다 확인하는 버튼은 없다.
   - '나머지 변경' 은 접혀 있고 판정하지 않는다. 사용자가 펼쳐 보고 피드백을 적을 수는 있다.
   - 나란히 보기와 한 줄로 보기를 바꿀 수 있다.
   - Enter 로 보내면 명령이 검토 결과를 찍고 끝난다. 탭은 스스로 닫히고 이야기 파일은 지워진다. HTML 파일은 남지 않는다.
   - 명령이 끝났다는 알림이 오면 그 출력을 읽는다. 답이 거기 있다.
   - `헤드리스 실행` 이 나오면(exit code 4) 띄우지 않은 것이다. 확인 단계를 건너뛰고 결과에 '구현 확인 안 받음 — 헤드리스 실행' 이라고 적는다.
     이 답은 `--status` · `--check` 에서도 나온다. 그때는 이야기를 쓰지 않고 바로 건너뛴다.
6. 결과를 읽고 이어 간다. 출력 끝의 `다음:` 줄이 할 일이다.
   - `기각` 인 그룹은 피드백대로 고친다. 고친 hunk 만 이야기에 담아 3~5를 다시 한다. 확인받은 hunk 를 다시 묻지 않는다.
   - 고치다가 확인받은 hunk 가 바뀌면 그 hunk 는 다시 나온다. 이야기에 담아 다시 확인받는다.
   - `확인함` 에 피드백이 달려 있으면 그 지적을 반영한다. 반영해서 바뀐 hunk 는 다시 확인받는다.
   - `미정` 인 그룹은 확인받지 못한 것이다. 확인받은 것으로 쓰지 않는다.
   - `구현이 확정됐다` 가 나오면 끝이다. 코드를 다시 쓰지 않는다. 다듬지도 않는다.
   - 결과에 '나머지 hunk N개는 사용자가 보지 않음' 을 적는다. 나머지 변경에 피드백이 달렸으면 반영한다.
   - 확정 뒤에 코드를 바꾸면(리뷰 지적 · 빌드 오류 수정) `--status` 가 남은 hunk 를 알려 준다. 그 가운데 동작이 바뀌는 hunk 는 그룹에 담아 다시 확인받는다.

## 규칙

- 핵심 그룹은 전부 확인받는다. 미정을 남긴 채 끝났다고 하지 않는다.
- 나머지 변경은 사용자가 보지 않는다. 자동 리뷰와 테스트가 본다. 동작이 바뀌는 hunk 를 나머지에 두지 않는다.
- 확정은 커밋이 아니다. 커밋 · 올리기는 사용자가 시킬 때 한다.
- 확인 기록은 `<프로젝트>/.claude/diff_confirmed.json` 이다. 스크립트만 쓴다. 직접 고치지 않고 커밋하지 않는다.
- 코드는 diff 에서만 온다. 페이지와 설계 문서에 내가 옮겨 적은 코드를 넣지 않는다. 내가 쓰는 것은 설계 포인트 · 왜 · 볼 것뿐이다.
- 핵심 코드를 입력 칸 없는 HTML 로 따로 만들지 않는다. 판정과 피드백을 그 자리에서 받을 수 없다.
- 한 줄에 사실 하나. 그룹 제목에 파일 이름 · 함수 이름을 늘어놓지 않는다.
- 바뀐 줄이 3000줄을 넘으면 `--path` 를 하위 폴더로 좁혀 나눠 낸다.
- 서버를 못 띄우면 `/selection` 의 '서버를 못 띄울 때' 와 같다. 이 경우 diff 를 대화에 표로 요약해 낸다.
